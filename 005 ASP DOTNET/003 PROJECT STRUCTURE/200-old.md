1. What Is the Old ASP.NET Core Architecture?

In ASP.NET Core 3.1 and .NET 5, the common web application structure was:

Program.cs
     +
Startup.cs

The responsibilities were separated.

Program.cs
     ↓
Create and start Host
     ↓
Startup.cs
     ├── ConfigureServices()
     │       ↓
     │   Dependency Injection
     │
     └── Configure()
             ↓
       Middleware Pipeline
             ↓
          Endpoints

17. Complete Startup.cs

A typical old ASP.NET Core application:

using Microsoft.AspNetCore.Builder;
using Microsoft.AspNetCore.Hosting;
using Microsoft.Extensions.Configuration;
using Microsoft.Extensions.DependencyInjection;
using Microsoft.Extensions.Hosting;
namespace MyProject
{
    public class Startup
    {
        public IConfiguration Configuration { get; }
        public Startup(IConfiguration configuration)
        {
            Configuration = configuration;
        }
        public void ConfigureServices(
            IServiceCollection services)
        {
            services.AddControllers();
            services.AddDbContext<AppDbContext>(
                options =>
                {
                    // Database configuration
                });
            services.AddHttpClient();
            services.AddMemoryCache();
            services.AddCors();
            services.AddAuthentication();
            services.AddAuthorization();
            services.AddSwaggerGen();
            services.AddScoped<
                IEmployeeService,
                EmployeeService>();
        }
        public void Configure(
            IApplicationBuilder app,
            IWebHostEnvironment env)
        {
            if (env.IsDevelopment())
            {
                app.UseDeveloperExceptionPage();
            }
            app.UseHttpsRedirection();
            app.UseStaticFiles();
            app.UseRouting();
            app.UseAuthentication();
            app.UseAuthorization();
            app.UseEndpoints(endpoints =>
            {
                endpoints.MapControllers();
            });
        }
    }
}

21. Service Lifetimes

There are three main DI lifetimes.

Transient

services.AddTransient<
    IMyService,
    MyService>();

A new instance is generally created each time it is requested.

⸻

Scoped

services.AddScoped<
    IMyService,
    MyService>();

For a web request, the same scoped instance is generally reused within that request scope.

Common for:

DbContext
Business services
Repositories

⸻

Singleton

services.AddSingleton<
    IMyService,
    MyService>();

One instance is used for the application’s lifetime.

34. What Is Middleware?

Middleware is software that participates in processing an HTTP request and response.

Basic idea:

Request
   ↓
Middleware 1
   ↓
Middleware 2
   ↓
Middleware 3
   ↓
Controller
   ↓
Response

Middleware can:

* Inspect request
* Modify request
* Stop request
* Call next middleware
* Modify response
* Handle exceptions
* Log information
* Authenticate
* Authorize
* Serve static files

⸻

35. app.Use()

One of the most important old ASP.NET Core concepts.

Basic syntax:

app.Use(async (context, next) =>
{
    // Before next middleware
    await next();
    // After next middleware
});

⸻

36. What Does app.Use() Mean?

app.Use() adds middleware to the pipeline.

Example:

app.Use(async (context, next) =>
{
    Console.WriteLine(
        "Request received");
    await next();
    Console.WriteLine(
        "Response completed");
});

⸻

37. next

This:

await next();

means:

Continue to the next middleware.

Without:

await next();

the request may stop at that middleware.

⸻

38. app.Use() Before and After

Consider:

app.Use(async (context, next) =>
{
    Console.WriteLine("A - Before");
    await next();
    Console.WriteLine("A - After");
});
app.Use(async (context, next) =>
{
    Console.WriteLine("B - Before");
    await next();
    Console.WriteLine("B - After");
});
app.Run(async context =>
{
    Console.WriteLine("C");
});

Output:

A - Before
B - Before
C
B - After
A - After

This is because middleware wraps the next middleware.

40. app.Run()

app.Run() adds terminal middleware.

Example:

app.Run(async context =>
{
    await context.Response.WriteAsync(
        "Hello");
});

Unlike normal Use() middleware, it does not call next.

It terminates the pipeline.

⸻

41. app.Use() vs app.Run()

app.Use()	app.Run()
Adds middleware	Adds terminal middleware
Can call next()	Does not normally call next
Request can continue	Pipeline ends
Can run before and after next	Handles final stage

43. UseMiddleware<T>()

Instead of writing inline middleware:

app.Use(async (context, next) =>
{
    ...
});

you can create a class.

public class LoggingMiddleware
{
    private readonly RequestDelegate _next;
    public LoggingMiddleware(
        RequestDelegate next)
    {
        _next = next;
    }
    public async Task InvokeAsync(
        HttpContext context)
    {
        Console.WriteLine(
            "Request received");
        await _next(context);
        Console.WriteLine(
            "Response completed");
    }
}

Register:

app.UseMiddleware<LoggingMiddleware>();

62. Middleware Ordering

Middleware executes in the order you register it.

Example:

app.UseA();
app.UseB();
app.UseC();

Request:

A
 ↓
B
 ↓
C
 ↓
Endpoint

Response comes back in reverse wrapping order:

Endpoint
 ↑
C
 ↑
B
 ↑
A

Therefore, order matters.

A common old ASP.NET Core 3.1 / .NET 5 API pipeline:

    IWebHostEnvironment env)
{
    if (env.IsDevelopment())
    {
        app.UseDeveloperExceptionPage();

    app.UseCors();
    app.UseAuthentication();
    app.UseAuthorization();
    app.UseEndpoints(endpoints =>

        endpoints.MapControllers();
    });

68. Custom Middleware That Stops a Request

You don’t always have to call next().

Example:

app.Use(async (context, next) =>
{
    if (context.Request.Method == "DELETE")
    {
        context.Response.StatusCode = 405;
        await context.Response.WriteAsync(
            "DELETE not allowed.");
        return;
    }
    await next();
});

Flow for DELETE:

DELETE request
      ↓
Custom middleware
      ↓
405 response
      ↓
STOP

The controller is never reached.

69. Your Existing app.Use() Pattern

Your earlier application had code similar to:

app.Use(async (context, next) =>
{
    var disallowedMethods =
        new[]
        {
            "HEAD",
            "TRACE",
            "PUT",
            "DELETE",
            "PATCH"
        };
    if (disallowedMethods.Contains(
        context.Request.Method.ToUpper()))
    {
        context.Response.StatusCode = 405;
        await context.Response.WriteAsync(
            "HTTP method not allowed.");
        return;
    }
    await next();
});

This is custom middleware.

It performs:

Request
  ↓
Check HTTP Method
  ↓
Allowed?
 ┌───────────────┐
 │               │
YES             NO
 │               │
 ▼               ▼
next()          405
 │               │
 ▼               STOP
Next middleware

70. Response.OnStarting()

You also had:

app.Use(async (context, next) =>
{
    context.Response.OnStarting(() =>
    {
        context.Response.Headers["X-Frame-Options"]
            = "DENY";
        return Task.CompletedTask;
    });
    await next();
});

OnStarting() registers a callback that executes just before the response headers are sent.

Useful for:

* Adding response headers
* Modifying headers
* Security headers

71. Custom Security Header Middleware

Example:

app.Use(async (context, next) =>
{
    context.Response.OnStarting(() =>
    {
        var headers = context.Response.Headers;
        headers["X-Frame-Options"] = "DENY";
        headers["X-Content-Type-Options"] =
            "nosniff";
        headers["Referrer-Policy"] =
            "no-referrer";
        return Task.CompletedTask;
    });
    await next();
});

Flow:

Request
   ↓
Register OnStarting()
   ↓
next()
   ↓
Controller
   ↓
Response begins
   ↓
OnStarting()
   ↓
Headers added

    public class Startup
    {
        public IConfiguration Configuration { get; }
        public Startup(
            IConfiguration configuration)
        {
            Configuration = configuration;
        }
        // -----------------------------
        // SERVICE REGISTRATION
        // -----------------------------
        public void ConfigureServices(
            IServiceCollection services)
        {
            // Controllers
            services.AddControllers();
            // Database
            services.AddDbContext<AppDbContext>(
                options =>
                {
                    // options.UseSqlServer(...);
                });
            // HTTP Client
            services.AddHttpClient();
            // Memory Cache
            services.AddMemoryCache();
            // CORS
            services.AddCors(options =>
            {
                options.AddPolicy(
                    "MyPolicy",
                    policy =>
                    {
                        policy
                            .AllowAnyOrigin()
                            .AllowAnyHeader()
                            .AllowAnyMethod();
                    });
            });
            // Authentication
            services.AddAuthentication();
            // Authorization
            services.AddAuthorization();
            // Swagger
            services.AddSwaggerGen();
            // Background Service
            services.AddHostedService<Worker>();
            // Application Services
            services.AddScoped<
                IEmployeeService,
                EmployeeService>();
        }
        // -----------------------------
        // HTTP PIPELINE
        // -----------------------------
        public void Configure(
            IApplicationBuilder app,
            IWebHostEnvironment env)
        {
            // Exception handling
            if (env.IsDevelopment())
            {
                app.UseDeveloperExceptionPage();
            }
            else
            {
                app.UseExceptionHandler("/Error");
                app.UseHsts();
            }
            // HTTPS
            app.UseHttpsRedirection();
            // Static files
            app.UseStaticFiles();
            // Custom request logging
            app.Use(async (context, next) =>
            {
                Console.WriteLine(
                    $"Request: " +
                    $"{context.Request.Method} " +
                    $"{context.Request.Path}");
                await next();
                Console.WriteLine(
                    $"Response: " +
                    $"{context.Response.StatusCode}");
            });
            // Routing
            app.UseRouting();
            // CORS
            app.UseCors("MyPolicy");
            // Authentication
            app.UseAuthentication();
            // Authorization
            app.UseAuthorization();
            // Swagger
            app.UseSwagger();
            app.UseSwaggerUI();
            // Endpoints
            app.UseEndpoints(endpoints =>
            {
                endpoints.MapControllers();
            });
        }
    }
}

76. Where Should Swagger Be?

You can configure Swagger middleware according to your application’s requirements.

For development-only Swagger:

if (env.IsDevelopment())
{
    app.UseSwagger();
    app.UseSwaggerUI();
}

For an internal/production API, you might intentionally enable it in other environments with appropriate security.

The important distinction is:

AddSwaggerGen()
    ↓
Service registration
UseSwagger()
UseSwaggerUI()
    ↓
Middleware/endpoints for Swagger

⸻

77. Where Should Custom Middleware Go?

Depends on what it needs.

Global exception handling

Put very early:

app.UseExceptionHandler(...);

Request logging

Usually early enough to see requests:

app.Use(async (context, next) =>
{
    ...
    await next();
});

Authentication-dependent middleware

Put after authentication.

Endpoint-specific logic

Put where routing/endpoint information is available.

⸻

78. Middleware Ordering Rule

Ask:

Does this middleware need something created by another middleware?

If yes, the dependency must come first.

Example:

Routing
   ↓
Authentication
   ↓
Authorization

because authorization depends on the authenticated user.

79. app.Use() Three Important Patterns

Pattern 1 — Continue

app.Use(async (context, next) =>
{
    // Before
    await next();
    // After
});

⸻

Pattern 2 — Stop

app.Use(async (context, next) =>
{
    if (someCondition)
    {
        context.Response.StatusCode = 403;
        return;
    }
    await next();
});

⸻

Pattern 3 — Modify Response

app.Use(async (context, next) =>
{
    await next();
    context.Response.Headers["X-App"] =
        "MyApplication";
});

Be careful: some response headers cannot be changed after the response has started. For those, use Response.OnStarting().

82. UseWhen()

Another advanced branching option:

app.UseWhen(
    context =>
        context.Request.Path.StartsWithSegments(
            "/admin"),
    branch =>
    {
        branch.UseMiddleware<
            AdminLoggingMiddleware>();
    });

Conceptually:

Request
   ↓
Condition
   ├── true  → Admin branch
   └── false → Normal pipeline

83. Old Architecture + Logging

Logging can be configured in old architecture using the host or Startup.

Example provider configuration:

public void Configure(
    IApplicationBuilder app,
    IWebHostEnvironment env,
    ILoggerFactory loggerFactory)
{
    // Configure logging provider here
}

For example, if the application has a file logging provider exposing AddFile():

string logDirectory =
    Path.Combine(
        Directory.GetCurrentDirectory(),
        "_Logs");
Directory.CreateDirectory(logDirectory);
string logPath =
    Path.Combine(
        logDirectory,
        "log.txt");
loggerFactory.AddFile(logPath);

Then application classes use:

ILogger<EmployeeService>

They don’t configure the file again.

85. BackgroundService in Old Architecture

Register it:

public void ConfigureServices(
    IServiceCollection services)
{
    services.AddHostedService<Worker>();
}

Worker:

public class Worker : BackgroundService
{
    private readonly ILogger<Worker>
        _logger;
    public Worker(
        ILogger<Worker> logger)
    {
        _logger = logger;
    }
    protected override async Task ExecuteAsync(
        CancellationToken stoppingToken)
    {
        _logger.LogInformation(
            "Worker started");
        while (!stoppingToken.IsCancellationRequested)
        {
            try
            {
                _logger.LogInformation(
                    "Job started");
                // Work
                _logger.LogInformation(
                    "Job completed");
            }
            catch (Exception ex)
            {
                _logger.LogError(
                    ex,
                    "Job failed");
            }
            await Task.Delay(
                60000,
                stoppingToken);
        }
    }
}

86. Does BackgroundService Have app.Use()?

No.

This is very important.

app.Use() belongs to the HTTP request pipeline.

A BackgroundService does not process HTTP requests through:

app.UseRouting()
app.UseCors()
app.UseAuthentication()

unless it is part of the same web application’s HTTP pipeline for separate requests.

BackgroundService has its own execution flow:

Host
 ↓
HostedService
 ↓
ExecuteAsync()
 ↓
Background Work

Means:
