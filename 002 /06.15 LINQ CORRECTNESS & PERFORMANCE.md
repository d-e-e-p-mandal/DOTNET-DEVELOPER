# 06.15 — LINQ CORRECTNESS & PERFORMANCE

**Chapter:** 06 — LINQ Fundamentals  
**Namespace:** `System.Linq`  
**Total Syllabus Topics:** 29

LINQ correctness means writing queries that produce the expected results under different conditions, including null values, empty collections, changing data, and deferred execution.

LINQ performance means reducing unnecessary processing, allocations, memory consumption, and repeated operations.

This section covers all **29 topics from your master syllabus**, without repeating the detailed explanations of LINQ operators from earlier sections.

# 1. Null Source vs Empty Sequence

A **null source** and an **empty sequence** are different.

- A null source means no sequence object is available.
- An empty sequence is a valid sequence containing zero elements.

### Example 1: Null source

```csharp
List<int>? numbers = null;

// Throws ArgumentNullException
var result = numbers!.Where(n => n > 10);
```

Most standard LINQ operators reject a null source.

### Example 2: Empty sequence

```csharp
List<int> numbers = new();

var result = numbers.Where(n => n > 10);

Console.WriteLine(result.Count());
```

**Output:**

```text
0
```

### Example 3: Null-safe LINQ

```csharp
List<int>? numbers = null;

var result = (numbers ?? Enumerable.Empty<int>())
    .Where(n => n > 10)
    .ToList();

Console.WriteLine(result.Count);
```

**Output:**

```text
0
```

### Example 4: Null-conditional operator

```csharp
List<int>? numbers = null;

int? count = numbers?.Count();

Console.WriteLine(count ?? 0);
```

**Output:**

```text
0
```

### Comparison

| Condition | Meaning | LINQ Behavior |
|---|---|---|
| `source == null` | No sequence object | Most LINQ operators throw |
| `source.Count == 0` | Valid empty collection | Operators can process it |
| `Enumerable.Empty<T>()` | Empty enumerable | Safe to enumerate |
| `source ?? Enumerable.Empty<T>()` | Null fallback | Provides an empty sequence |

**Key point:** Use an empty sequence when the intended meaning is “no elements,” rather than using null unnecessarily.

# 2. Null Elements

A sequence can be non-null while containing null elements.

### Example 1: Null elements in a list

```csharp
List<string?> names = new()
{
    "Amit",
    null,
    "Rahul",
    null
};
```

The list is valid, but some elements are null.

### Example 2: Unsafe property access

```csharp
var result = names.Where(name => name!.Length > 4);

// Throws NullReferenceException during enumeration
```

The null-forgiving operator `!` suppresses a compiler warning; it does not prevent runtime null exceptions.

### Example 3: Safe filtering

```csharp
var result = names
    .Where(name => name != null && name.Length > 4)
    .ToList();

Console.WriteLine(string.Join(", ", result));
```

**Output:**

```text
Rahul
```

### Example 4: Remove null elements

```csharp
List<string> result = names
    .OfType<string>()
    .ToList();
```

**Result:**

```text
Amit, Rahul
```

### Example 5: Null-safe projection

```csharp
var result = names.Select(name => name?.Length ?? 0);

Console.WriteLine(string.Join(", ", result));
```

**Output:**

```text
4, 0, 5, 0
```

**Key point:** Check whether individual elements can be null before accessing their members.

# 3. Nullable Values

Nullable value types allow value-type variables to represent either a value or null.

### Syntax

```csharp
int? number = null;
```

### Example 1: Nullable integer sequence

```csharp
int?[] numbers = { 10, null, 20, null, 30 };

var result = numbers.Where(n => n.HasValue);

Console.WriteLine(result.Count());
```

**Output:**

```text
3
```

### Example 2: Extract non-null values

```csharp
int?[] numbers = { 10, null, 20, 30 };

List<int> result = numbers
    .Where(n => n.HasValue)
    .Select(n => n.Value)
    .ToList();
```

**Result:**

```text
10, 20, 30
```

### Example 3: Default for null values

```csharp
int?[] numbers = { 10, null, 20 };

var result = numbers.Select(n => n ?? 0);

Console.WriteLine(string.Join(", ", result));
```

**Output:**

```text
10, 0, 20
```

### Example 4: Nullable aggregation

```csharp
int?[] numbers = { 10, null, 20 };

int? sum = numbers.Sum();

Console.WriteLine(sum);
```

**Output:**

```text
30
```

For nullable numeric sequences, standard LINQ `Sum()` ignores null values.

**Key point:** Nullable values require explicit consideration of missing data, especially during projection and aggregation.

# 4. Nullable Reference Types

Nullable reference types help the compiler identify potentially unsafe null access.

This feature is available when nullable reference-type analysis is enabled.

### Example 1: Non-nullable reference

```csharp
string name = "Amit";
```

### Example 2: Nullable reference

```csharp
string? name = null;
```

### Example 3: Nullable collection elements

```csharp
List<string?> names = new()
{
    "Amit",
    null,
    "Rahul"
};
```

### Example 4: Null-safe LINQ

```csharp
var lengths = names
    .Where(name => name is not null)
    .Select(name => name.Length)
    .ToList();
```

**Result:**

```text
4, 5
```

### Example 5: Nullable property

```csharp
public class Student
{
    public string Name { get; set; } = "";
    public string? Department { get; set; }
}
```

```csharp
var result = students
    .Where(s => s.Department != null)
    .Select(s => s.Department);
```

### Important distinction

```csharp
List<string>? names;
```

The list itself may be null.

```csharp
List<string?> names;
```

The list is declared non-nullable, but its elements may be null.

```csharp
List<string?>? names;
```

Both the list and its elements may be null.

**Key point:** Nullable annotations improve static analysis, but they do not add runtime null checks automatically.

# 5. Default Values

Some LINQ operators return default values when a sequence is empty or no matching element exists.

### Example 1: FirstOrDefault

```csharp
int[] numbers = { 10, 20, 30 };

int result = numbers.FirstOrDefault(n => n > 100);

Console.WriteLine(result);
```

**Output:**

```text
0
```

### Example 2: Reference type default

```csharp
string[] names = { "Amit", "Rahul" };

string? result = names.FirstOrDefault(
    name => name == "Priya"
);

Console.WriteLine(result is null);
```

**Output:**

```text
True
```

### Example 3: Explicit fallback

```csharp
int[] numbers = { 10, 20, 30 };

int result = numbers.FirstOrDefault(
    n => n > 100,
    -1
);

Console.WriteLine(result);
```

**Output:**

```text
-1
```

### Example 4: Avoid ambiguous defaults

```csharp
int[] numbers = { 0, 10, 20 };

int result = numbers.FirstOrDefault(n => n < 5);
```

The result is `0`, but this value also represents the default of `int`.

If distinguishing “found” from “not found” matters, use a suitable explicit fallback, nullable result, or separate existence check.

**Key point:** A default value is not necessarily evidence that no matching element exists.

# 6. Multiple Enumeration

Multiple enumeration means iterating over the same enumerable more than once.

The execution behavior was explained in Section 06.11. Here, the focus is avoiding unnecessary work.

### Example 1: Multiple enumeration

```csharp
IEnumerable<int> numbers = Enumerable.Range(1, 100);

int count = numbers.Count();

int sum = numbers.Sum();
```

The sequence is accessed by two terminal operations.

Depending on the source and implementation, this may require repeated processing.

### Example 2: Expensive query

```csharp
var query = numbers.Select(n =>
{
    Console.WriteLine($"Processing {n}");
    return n * 2;
});

int count = query.Count();
int sum = query.Sum();
```

The projection may execute more than once.

### Example 3: Materialize when reuse is needed

```csharp
List<int> result = numbers
    .Select(n => n * 2)
    .ToList();

int count = result.Count;
int sum = result.Sum();
```

### Important consideration

Materialization is not always necessary.

For arrays and lists, operations such as obtaining `Length` or `Count` can already be efficient.

**Key point:** Avoid repeated expensive enumeration, but do not materialize every sequence automatically.

# 7. Unnecessary Materialization

Unnecessary materialization creates intermediate collections that are not required.

### Example 1: Unnecessary ToList

```csharp
var result = numbers
    .Where(n => n > 10)
    .ToList()
    .Select(n => n * 2)
    .ToList();
```

The first `ToList()` creates an intermediate collection.

### Better approach

```csharp
var result = numbers
    .Where(n => n > 10)
    .Select(n => n * 2)
    .ToList();
```

Only the final result is materialized.

### Example 2: Unnecessary ToArray

```csharp
bool exists = numbers
    .Where(n => n > 10)
    .ToArray()
    .Any();
```

### Better approach

```csharp
bool exists = numbers.Any(n => n > 10);
```

### Example 3: Unnecessary collection for Count

```csharp
int count = numbers
    .Where(n => n > 10)
    .ToList()
    .Count;
```

### Better approach

```csharp
int count = numbers.Count(n => n > 10);
```

**Key point:** Materialize only when a concrete collection, reusable result, or snapshot is actually required.

# 8. Repeated Sorting

Sorting can be expensive because it requires comparing and arranging elements.

### Example 1: Repeated sorting

```csharp
var query = numbers.OrderBy(n => n);

var first = query.ToList();
var second = query.ToList();
```

The deferred sorting operation is executed for each enumeration.

### Example 2: Sort once

```csharp
var sorted = numbers
    .OrderBy(n => n)
    .ToList();

var first = sorted.Take(5).ToList();
var second = sorted.Skip(5).Take(5).ToList();
```

### Example 3: Avoid independent sorts

```csharp
var first = numbers.OrderBy(n => n).First();

var last = numbers.OrderBy(n => n).Last();
```

If only the minimum and maximum are required, use:

```csharp
int minimum = numbers.Min();
int maximum = numbers.Max();
```

### Example 4: Sort after filtering

```csharp
var result = numbers
    .Where(n => n > 100)
    .OrderBy(n => n)
    .ToList();
```

This reduces the number of elements that must be sorted when the filter removes values.

**Key point:** Reuse sorted results when appropriate and avoid sorting data when an aggregate or selection operation is sufficient.

# 9. Repeated Filtering

Repeated filtering can cause the same predicates to execute multiple times.

### Example 1: Duplicate filtering

```csharp
var first = numbers.Where(n => n > 10).Count();

var second = numbers.Where(n => n > 10).Sum();
```

### Example 2: Define a reusable query

```csharp
var filtered = numbers.Where(n => n > 10);

int count = filtered.Count();
int sum = filtered.Sum();
```

This improves code reuse but does not necessarily prevent repeated predicate evaluation.

### Example 3: Materialize filtered results

```csharp
var filtered = numbers
    .Where(n => n > 10)
    .ToList();

int count = filtered.Count;
int sum = filtered.Sum();
```

### Example 4: Combine filters

```csharp
var result = numbers
    .Where(n => n > 10)
    .Where(n => n % 2 == 0);
```

Equivalent logical condition:

```csharp
var result = numbers.Where(
    n => n > 10 && n % 2 == 0
);
```

Combining predicates can improve clarity and sometimes reduce overhead, although performance depends on the source and implementation.

# 10. Early Filtering

Early filtering removes unnecessary elements before expensive operations.

### Example 1: Filter before projection

```csharp
var result = students
    .Where(s => s.Marks >= 80)
    .Select(s => ExpensiveTransform(s))
    .ToList();
```

Only matching students are transformed.

### Example 2: Less efficient order

```csharp
var result = students
    .Select(s => ExpensiveTransform(s))
    .Where(x => x.Marks >= 80)
    .ToList();
```

Here, every student is transformed before filtering.

### Example 3: Filter before sorting

```csharp
var result = students
    .Where(s => s.Marks >= 80)
    .OrderBy(s => s.Name)
    .ToList();
```

### Example 4: Database filtering

```csharp
var result = db.Students
    .Where(s => s.Marks >= 80)
    .ToList();
```

With a supported EF Core provider, filtering can occur in the database.

**Important:** Reordering operations is only valid when it preserves the query's intended semantics. Filters cannot always be moved across projections, grouping, pagination, or other operators.

# 11. Narrow Projection

Narrow projection means selecting only the data required by the application.

### Example 1: Full objects

```csharp
var result = db.Students.ToList();
```

This retrieves complete mapped student entities.

### Example 2: Select required properties

```csharp
var result = db.Students
    .Select(s => new
    {
        s.Name,
        s.Marks
    })
    .ToList();
```

A relational provider can often generate SQL that retrieves only the selected columns.

### Example 3: DTO projection

```csharp
public record StudentDto(
    string Name,
    int Marks
);
```

```csharp
var result = db.Students
    .Select(s => new StudentDto(
        s.Name,
        s.Marks
    ))
    .ToList();
```

### Example 4: Select a single property

```csharp
var names = db.Students
    .Select(s => s.Name)
    .ToList();
```

### Benefits

- Less data transfer.
- Reduced memory usage.
- Smaller result objects.
- Potentially faster database queries.
- Clearer output contracts.

**Key point:** Select only the fields needed, especially when querying remote data sources.

# 12. `Any()` vs `Count() > 0`

Both expressions can determine whether a sequence contains elements.

However, their execution characteristics can differ.

### Example 1: Any

```csharp
bool exists = numbers.Any();
```

### Example 2: Count

```csharp
bool exists = numbers.Count() > 0;
```

### Example 3: Any with condition

```csharp
bool exists = numbers.Any(n => n > 100);
```

### Example 4: Count with condition

```csharp
bool exists = numbers.Count(n => n > 100) > 0;
```

### Comparison

| Feature | `Any()` | `Count() > 0` |
|---|---|---|
| Purpose | Check existence | Count and compare |
| Can stop after first match | Yes | Generally counts all matches |
| Collection optimizations | Possible | Possible |
| Typical existence-check choice | Preferred | Usually unnecessary |

For database queries, providers may translate `Any()` into an efficient existence check.

**Key point:** Use `Any()` when the question is simply whether at least one matching element exists.

# 13. First vs Single

`First()` and `Single()` enforce different correctness requirements.

### Example 1: First

```csharp
int[] numbers = { 10, 20, 30 };

int result = numbers.First();

Console.WriteLine(result);
```

**Output:**

```text
10
```

### Example 2: Single

```csharp
int[] numbers = { 10 };

int result = numbers.Single();

Console.WriteLine(result);
```

**Output:**

```text
10
```

### Example 3: Single with multiple elements

```csharp
int[] numbers = { 10, 20 };

int result = numbers.Single();
```

**Result:**

```text
InvalidOperationException
```

### Example 4: First with multiple matches

```csharp
int[] numbers = { 10, 20, 30 };

int result = numbers.First(n => n > 10);

// Output: 20
```

### Comparison

| Operator | Empty Sequence | One Element | Multiple Elements |
|---|---|---|---|
| `First()` | Throws | Returns first | Returns first |
| `FirstOrDefault()` | Returns default | Returns first | Returns first |
| `Single()` | Throws | Returns element | Throws |
| `SingleOrDefault()` | Returns default | Returns element | Throws |

**Key point:** Choose `Single()` when exactly one match is required by the business rules. Choose `First()` when only the first match is needed.

# 14. `TryGetNonEnumeratedCount`

`TryGetNonEnumeratedCount()` attempts to determine a sequence's element count without enumerating its elements.

**Available since:** .NET 6

### Syntax

```csharp
bool success = source.TryGetNonEnumeratedCount(
    out int count
);
```

### Example 1: Array

```csharp
int[] numbers = { 1, 2, 3, 4, 5 };

bool success = numbers.TryGetNonEnumeratedCount(
    out int count
);

Console.WriteLine(success);
Console.WriteLine(count);
```

**Output:**

```text
True
5
```

### Example 2: List

```csharp
List<int> numbers = new() { 10, 20, 30 };

bool success = numbers.TryGetNonEnumeratedCount(
    out int count
);
```

**Result:**

```text
success = true
count = 3
```

### Example 3: Iterator sequence

```csharp
IEnumerable<int> Generate()
{
    yield return 10;
    yield return 20;
    yield return 30;
}

var source = Generate();

bool success = source.TryGetNonEnumeratedCount(
    out int count
);
```

For this iterator, the count generally cannot be determined without enumeration.

**Expected result:**

```text
success = false
count = 0
```

### Example 4: Fallback

```csharp
int count;

if (!source.TryGetNonEnumeratedCount(out count))
{
    count = source.Count();
}

Console.WriteLine(count);
```

**Important:** A return value of `false` does not mean the sequence is empty. It means the count could not be determined without enumeration.

# 15. Iterator Overhead

LINQ operators often use iterators to process sequences.

Iterators provide composability and deferred execution, but they can introduce additional method calls and state management.

### Example 1: LINQ

```csharp
int sum = numbers
    .Where(n => n > 10)
    .Sum();
```

### Example 2: Equivalent loop

```csharp
int sum = 0;

foreach (int n in numbers)
{
    if (n > 10)
    {
        sum += n;
    }
}
```

### Potential overhead

```text
LINQ Pipeline
     │
     ├── Iterator State
     ├── Predicate Invocation
     ├── MoveNext Calls
     └── Enumeration Logic
```

The exact overhead depends on the .NET runtime, source collection, and operators.

### When it matters

- Very large collections.
- Performance-critical loops.
- Repeated execution.
- Small operations performed millions of times.

**Key point:** Iterator overhead is usually acceptable for ordinary application code. Measure before replacing LINQ with loops.

---

# 16. Delegate Overhead

LINQ predicates and selectors commonly use delegates.

Delegate invocation can introduce overhead compared with directly executing an operation inside a loop.

### Example 1: LINQ delegate

```csharp
int[] numbers = { 1, 2, 3, 4, 5 };

var result = numbers.Where(n => n > 2);
```

### Example 2: Explicit delegate

```csharp
Func<int, bool> predicate = n => n > 2;

var result = numbers.Where(predicate);
```

### Example 3: Local method

```csharp
bool IsGreaterThanTwo(int n)
{
    return n > 2;
}

var result = numbers.Where(IsGreaterThanTwo);
```

### Example 4: Direct loop

```csharp
foreach (int n in numbers)
{
    if (n > 2)
    {
        Console.WriteLine(n);
    }
}
```

### Performance considerations

- Delegate calls may have overhead.
- JIT optimizations can reduce some overhead.
- LINQ implementations include specialized optimizations.
- Different runtimes may produce different results.

**Key point:** Delegate overhead matters primarily in performance-sensitive paths, not as a reason to avoid LINQ everywhere.

# 17. Closure Allocation

A closure occurs when a lambda captures variables from its surrounding scope.

Capturing local state may require an additional object to hold that state.

### Example 1: Capturing lambda

```csharp
int minimum = 10;

var result = numbers.Where(n => n > minimum);
```

The lambda captures `minimum`.

### Example 2: Non-capturing lambda

```csharp
var result = numbers.Where(n => n > 10);
```

The lambda does not capture an external local variable.

### Example 3: Static lambda

```csharp
var result = numbers.Where(
    static n => n > 10
);
```

The `static` modifier prevents the lambda from capturing local variables or instance state.

### Example 4: Invalid static capture

```csharp
int minimum = 10;

// Compilation error:
// var result = numbers.Where(static n => n > minimum);
```

### Comparison

| Lambda | Captures State? |
|---|---|
| `n => n > 10` | No |
| `n => n > minimum` | Yes |
| `static n => n > 10` | No |
| `static n => n > minimum` | Not allowed |

**Important:** Capturing does not guarantee a new allocation every time the lambda runs. Allocation behavior depends on compiler and runtime implementation.

# 18. Sorting Cost

Sorting generally requires more work than a simple linear scan.

### Typical complexity

For comparison-based sorting:

\[
O(n \log n)
\]

where \(n\) is the number of elements.

### Example 1: Sort complete sequence

```csharp
var result = numbers
    .OrderBy(n => n)
    .ToList();
```

### Example 2: Find minimum without sorting

```csharp
int minimum = numbers.Min();
```

A minimum scan typically requires:

\[
O(n)
\]

### Example 3: Find maximum

```csharp
int maximum = numbers.Max();
```

### Example 4: Filter before sorting

```csharp
var result = numbers
    .Where(n => n > 100)
    .OrderBy(n => n)
    .ToList();
```

### Complexity comparison

| Operation | Typical Time Complexity |
|---|---|
| `Min()` | \(O(n)\) |
| `Max()` | \(O(n)\) |
| `Where()` | \(O(n)\) for full enumeration |
| `OrderBy()` | \(O(n \log n)\) |
| `OrderBy().ToList()` | \(O(n \log n)\) |

**Key point:** Do not sort a complete sequence when only a minimum, maximum, or existence check is required.

# 19. Buffering Cost

Some LINQ operators must buffer data before producing results.

### Example 1: Sorting

```csharp
var query = numbers.OrderBy(n => n);
```

When enumerated, `OrderBy()` generally buffers the source before yielding sorted elements.

### Example 2: Grouping

```csharp
var query = students.GroupBy(s => s.Marks);
```

Grouping builds internal structures to organize elements.

### Example 3: Streaming filter

```csharp
var query = numbers.Where(n => n > 10);
```

Filtering can produce matching elements incrementally.

### Comparison

| Operator | Buffering Behavior |
|---|---|
| `Where()` | Streaming |
| `Select()` | Streaming |
| `Take()` | Streaming |
| `OrderBy()` | Buffers source |
| `GroupBy()` | Builds groups |
| `Reverse()` | Buffers general enumerable sources |

**Key point:** Buffering can increase memory consumption and delay the first result.

# 20. Materialization Cost

Materialization stores query results in a concrete collection.

### Example 1: ToList

```csharp
var result = numbers.ToList();
```

### Example 2: ToArray

```csharp
var result = numbers.ToArray();
```

### Example 3: Multiple materializations

```csharp
var first = numbers.ToList();

var second = first.ToArray();

var third = second.ToList();
```

This creates multiple collections.

### Better approach

```csharp
var result = numbers.ToList();
```

Materialize into the final required collection type.

### Typical costs

- Allocating collection storage.
- Copying element values or references.
- Enumerating the source.
- Potentially resizing internal storage.
- Retaining results in memory.

**Key point:** Materialization is useful, but unnecessary intermediate collections increase memory and processing costs.

# 21. Memory Usage

LINQ memory consumption depends on the operators, source type, and result type.

### Example 1: Deferred filter

```csharp
IEnumerable<int> result = numbers.Where(n => n > 10);
```

The query does not immediately create a collection containing all matching values.

### Example 2: Materialized filter

```csharp
List<int> result = numbers
    .Where(n => n > 10)
    .ToList();
```

The matching values are stored in a new list.

### Example 3: Large array

```csharp
int[] result = Enumerable.Range(1, 1_000_000)
    .ToArray();
```

The array stores one million integers.

### Example 4: Avoid unnecessary storage

```csharp
long count = Enumerable.Range(1, 1_000_000)
    .LongCount(n => n % 2 == 0);
```

This calculates the result without creating a list of matching values.

### Memory comparison

| Approach | Additional Memory |
|---|---|
| Streaming `Where()` | Usually small |
| Streaming `Select()` | Usually small |
| `ToList()` | Proportional to result size |
| `ToArray()` | Proportional to result size |
| `OrderBy()` | Proportional to source size |
| `GroupBy()` | Proportional to grouped data |

# 22. Large Sequences

Large sequences require attention to memory usage, enumeration cost, and query execution strategy.

### Example 1: Large generated sequence

```csharp
IEnumerable<int> numbers =
    Enumerable.Range(1, 10_000_000);
```

### Example 2: Streaming processing

```csharp
long sum = numbers
    .Where(n => n % 2 == 0)
    .Sum(n => (long)n);
```

This calculates the sum without materializing all matching values.

### Example 3: Limit results

```csharp
var result = numbers
    .Where(n => n % 2 == 0)
    .Take(100)
    .ToList();
```

Only 100 matching elements are stored.

### Example 4: Pagination

```csharp
int pageNumber = 3;
int pageSize = 100;

var result = numbers
    .Skip((pageNumber - 1) * pageSize)
    .Take(pageSize)
    .ToList();
```

### Example 5: Database pagination

```csharp
var result = db.Students
    .OrderBy(s => s.Id)
    .Skip(200)
    .Take(100)
    .ToList();
```

For databases, stable ordering is important when paginating.

### Recommendations

- Prefer streaming where appropriate.
- Avoid materializing huge sequences unnecessarily.
- Limit result sizes.
- Apply filters early.
- Use database-side filtering and pagination when available.
- Consider cancellation and resource limits for long-running operations.

# 23. Side Effects in Queries

LINQ predicates and selectors should generally avoid modifying external state.

Side effects can behave unexpectedly because of deferred execution and repeated enumeration.

### Example 1: Side effect

```csharp
int counter = 0;

var query = numbers.Select(n =>
{
    counter++;
    return n * 2;
});
```

### Example 2: Query not executed

```csharp
Console.WriteLine(counter);
```

**Output:**

```text
0
```

### Example 3: Execute query

```csharp
var result = query.ToList();

Console.WriteLine(counter);
```

The counter increases when elements are processed.

### Example 4: Repeated execution

```csharp
query.ToList();
```

The counter increases again.

### Better approach

```csharp
var result = numbers
    .Select(n => n * 2)
    .ToList();

int processedCount = result.Count;
```

**Key point:** Prefer pure transformations and perform required side effects explicitly outside the query.

---

# 24. Mutation during Enumeration

Modifying a collection while it is being enumerated can invalidate its enumerator.

### Example 1: Unsafe mutation

```csharp
List<int> numbers = new() { 1, 2, 3, 4 };

foreach (int n in numbers)
{
    if (n == 2)
    {
        numbers.Remove(n);
    }
}
```

**Result:**

```text
InvalidOperationException
```

### Example 2: Safe RemoveAll

```csharp
List<int> numbers = new() { 1, 2, 3, 4 };

numbers.RemoveAll(n => n % 2 == 0);

Console.WriteLine(string.Join(", ", numbers));
```

**Output:**

```text
1, 3
```

### Example 3: Iterate over snapshot

```csharp
List<int> numbers = new() { 1, 2, 3, 4 };

foreach (int n in numbers.ToList())
{
    if (n % 2 == 0)
    {
        numbers.Remove(n);
    }
}
```

### Example 4: Create a filtered collection

```csharp
List<int> numbers = new() { 1, 2, 3, 4 };

numbers = numbers
    .Where(n => n % 2 != 0)
    .ToList();
```

**Key point:** Avoid modifying ordinary collections during active enumeration unless the collection explicitly supports the intended concurrent or mutation behavior.

# 25. Deferred-Execution Bugs

Deferred execution can introduce bugs when query execution occurs later than expected.

### Example 1: Source changes

```csharp
List<int> numbers = new() { 1, 2, 3 };

var query = numbers.Where(n => n > 1);

numbers.Add(4);

var result = query.ToList();
```

**Result:**

```text
2, 3, 4
```

The query observes the later addition.

### Example 2: Captured variable changes

```csharp
int minimum = 10;

var query = numbers.Where(n => n > minimum);

minimum = 20;

var result = query.ToList();
```

The predicate uses the updated value.

### Example 3: Exception occurs later

```csharp
var query = numbers.Select(n => 100 / n);
```

If the sequence contains zero, the division exception occurs when the problematic element is processed.

### Example 4: Query uses disposed resources

```csharp
IEnumerable<Student> GetStudents()
{
    using var db = new AppDbContext();

    return db.Students.Where(s => s.Marks > 80);
}
```

This is unsafe because the returned deferred query depends on a context that has already been disposed.

### Better approach

```csharp
List<Student> GetStudents()
{
    using var db = new AppDbContext();

    return db.Students
        .Where(s => s.Marks > 80)
        .ToList();
}
```

Here, `AppDbContext` represents a properly configured EF Core context.

**Key point:** Understand when the query executes and which resources it requires at that time.

# 26. IEnumerable/IQueryable Confusion

Confusing `IEnumerable<T>` and `IQueryable<T>` can cause unintended client-side processing.

### Example 1: IQueryable

```csharp
IQueryable<Student> query = db.Students;

var result = query
    .Where(s => s.Marks >= 80)
    .ToList();
```

The provider can translate the filter.

### Example 2: IEnumerable

```csharp
IEnumerable<Student> query = db.Students;

var result = query
    .Where(s => s.Marks >= 80)
    .ToList();
```

Because the variable is typed as `IEnumerable<Student>`, the subsequent `Where()` resolves to `Enumerable.Where()`.

This can cause filtering to occur in the application rather than in the database.

### Example 3: Explicit boundary

```csharp
var result = db.Students
    .Where(s => s.Marks >= 80)
    .AsEnumerable()
    .Where(s => CustomCheck(s))
    .ToList();
```

### Example 4: Avoid unnecessary conversion

```csharp
var result = db.Students
    .AsEnumerable()
    .Where(s => s.Marks >= 80)
    .ToList();
```

This may retrieve more database rows than necessary.

### Correct approach

```csharp
var result = db.Students
    .Where(s => s.Marks >= 80)
    .ToList();
```

**Key point:** Preserve `IQueryable<T>` while composing operations that should execute through the query provider.

# 27. Choosing LINQ vs Loop

LINQ and loops are both valid approaches.

The choice depends on readability, execution requirements, and measured performance.

### Example 1: LINQ

```csharp
int[] numbers = { 1, 2, 3, 4, 5 };

var result = numbers
    .Where(n => n % 2 == 0)
    .Select(n => n * 10)
    .ToList();
```

**Result:**

```text
20, 40
```

### Example 2: Equivalent loop

```csharp
List<int> result = new();

foreach (int n in numbers)
{
    if (n % 2 == 0)
    {
        result.Add(n * 10);
    }
}
```

### Example 3: LINQ aggregation

```csharp
int sum = numbers.Sum();
```

### Example 4: Loop aggregation

```csharp
int sum = 0;

foreach (int n in numbers)
{
    sum += n;
}
```

### Comparison

| Requirement | Often Prefer |
|---|---|
| Simple filtering and projection | LINQ |
| Readable declarative queries | LINQ |
| Grouping and joining | LINQ |
| Complex mutation | Loop |
| Fine-grained control flow | Loop |
| Performance-critical hot path | Benchmark both |
| Early exit with custom behavior | Loop or suitable LINQ terminal operator |
| Query provider translation | LINQ with `IQueryable<T>` |

**Key point:** Prefer the clearest correct implementation first. Optimize performance-critical code using measurements.

# 28. Benchmarking Representative Queries

Benchmarking measures the performance of actual implementations under controlled conditions.

For .NET, **BenchmarkDotNet** is a commonly used benchmarking library.

### Example 1: LINQ benchmark

```csharp
using BenchmarkDotNet.Attributes;

[MemoryDiagnoser]
public class LinqBenchmarks
{
    private readonly int[] numbers =
        Enumerable.Range(1, 100_000).ToArray();

    [Benchmark]
    public int LinqSum()
    {
        return numbers
            .Where(n => n % 2 == 0)
            .Sum();
    }
}
```

### Example 2: Loop benchmark

```csharp
[Benchmark]
public int LoopSum()
{
    int sum = 0;

    foreach (int n in numbers)
    {
        if (n % 2 == 0)
        {
            sum += n;
        }
    }

    return sum;
}
```

These two benchmark methods belong inside the same `LinqBenchmarks` class.

### Example 3: Run benchmarks

```csharp
using BenchmarkDotNet.Running;

BenchmarkRunner.Run<LinqBenchmarks>();
```

Install the BenchmarkDotNet NuGet package before running the example.

### Important benchmarking factors

- Input size.
- Input data distribution.
- Runtime version.
- Release vs Debug build.
- Warm-up and JIT compilation.
- Allocations.
- Garbage collection.
- Query complexity.
- Repeated enumeration.
- Database or network latency.

### Example benchmark categories

| Test | What to Compare |
|---|---|
| Filtering | `Where()` vs loop |
| Projection | `Select()` vs loop |
| Aggregation | `Sum()` vs loop |
| Materialization | `ToArray()` vs `ToList()` |
| Sorting | `OrderBy()` vs alternative approaches |
| Repeated enumeration | Deferred vs cached results |
| Database filtering | Server-side vs client-side |
| Large sequences | Streaming vs materialization |

**Important:** A benchmark must use representative data and consume the computed result. Otherwise, the compiler or runtime may optimize away work that the application actually needs.

| Check | Question |
|---|---|
| Null safety | Can the source or its elements be null? |
| Empty sequences | Is an empty result handled correctly? |
| Default values | Could a default value be mistaken for a real match? |
| Enumeration | Is the query executed more than necessary? |
| Materialization | Are intermediate collections required? |
| Filtering | Can irrelevant elements be removed earlier? |
| Projection | Are unnecessary fields being retrieved? |
| Sorting | Is sorting required? |
| Aggregation | Can `Min`, `Max`, `Sum`, or `Any` replace sorting or counting? |
| Buffering | Does the query store the entire source? |
| Memory | Is the result collection too large? |
| Closures | Does the lambda capture unnecessary state? |
| Side effects | Does the query mutate external state? |
| Mutation | Can the source change during enumeration? |
| Deferred execution | Is the query executed at the intended time? |
| Query provider | Are operations executing locally or remotely? |
| Benchmarking | Has the performance difference been measured? |
