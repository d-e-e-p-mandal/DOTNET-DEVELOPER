# 09.12 — TESTING FUNCTIONAL CODE

**Chapter:** 09 — Functional C#  
**Total Syllabus Points:** 18  
**Language:** C#  
**Level:** Beginner → Advanced

Functional code is particularly suitable for testing because pure functions have explicit inputs, predictable outputs, and no observable side effects.

Testing functional code involves verifying individual functions, mathematical properties, transformation pipelines, error handling, and interactions with external systems.

This section covers all **18 points from your syllabus in their original order**, with explanations, C# examples, expected outputs, and practical testing techniques.

---

## 1. Deterministic Tests

A **deterministic test** produces the same result whenever it runs under the same conditions.

For a pure function:

```text
Same Input → Same Output
```

### Example 1: Deterministic function

```csharp
static int Add(int a, int b)
{
    return a + b;
}

Console.WriteLine(Add(10, 20));
Console.WriteLine(Add(10, 20));
```

**Output:**

```text
30
30
```

The result is always `30` for those inputs.

### Example 2: Deterministic test using xUnit

```csharp
using Xunit;

public class CalculatorTests
{
    [Fact]
    public void Add_ReturnsCorrectSum()
    {
        int result = Add(10, 20);

        Assert.Equal(30, result);
    }

    private static int Add(int a, int b)
    {
        return a + b;
    }
}
```

**Test result:**

```text
Passed: Add_ReturnsCorrectSum
```

### Example 3: Nondeterministic dependency

```csharp
static int GenerateNumber()
{
    return Random.Shared.Next(1, 101);
}
```

A test that expects a particular number would be unreliable.

### Deterministic alternative

```csharp
static int CalculateReward(int randomNumber)
{
    return randomNumber * 10;
}
```

```csharp
[Fact]
public void CalculateReward_ReturnsExpectedValue()
{
    Assert.Equal(50, CalculateReward(5));
}
```

The random value is supplied explicitly.

### Deterministic testing principles

| Principle | Explanation |
|---|---|
| Fixed inputs | Use known test values |
| Predictable outputs | Expect exact results |
| Controlled time | Pass time explicitly |
| Controlled randomness | Supply generated values |
| Isolated state | Avoid shared mutable dependencies |

**Key point:** Deterministic tests produce repeatable results independent of changing external conditions.

## 2. Pure Function Testing

**Pure function testing** verifies a function using only its inputs and returned outputs.

Pure functions are easier to test because they do not require databases, files, networks, or other external systems.

### Example 1: Pure calculation

```csharp
public static class Calculator
{
    public static int Square(int number)
    {
        return number * number;
    }
}
```

### Test

```csharp
using Xunit;

public class CalculatorTests
{
    [Fact]
    public void Square_ReturnsCorrectResult()
    {
        int result = Calculator.Square(5);

        Assert.Equal(25, result);
    }
}
```

**Test result:**

```text
Passed
```

### Example 2: Pure discount calculation

```csharp
public static class PriceCalculator
{
    public static decimal ApplyDiscount(
        decimal price,
        decimal discountRate)
    {
        return price * (1 - discountRate);
    }
}
```

### Test

```csharp
[Fact]
public void ApplyDiscount_ReturnsDiscountedPrice()
{
    decimal result =
        PriceCalculator.ApplyDiscount(
            1000m,
            0.10m
        );

    Assert.Equal(900m, result);
}
```

### Example 3: Pure LINQ transformation

```csharp
public static int[] DoubleNumbers(
    IEnumerable<int> numbers)
{
    return numbers
        .Select(x => x * 2)
        .ToArray();
}
```

### Test

```csharp
[Fact]
public void DoubleNumbers_TransformsAllElements()
{
    int[] input = { 1, 2, 3 };

    int[] result = DoubleNumbers(input);

    Assert.Equal(
        new[] { 2, 4, 6 },
        result
    );
}
```

### Advantages

- No external setup is required.
- Tests execute quickly.
- Failures are easier to reproduce.
- Tests can run independently.
- Results are predictable.

**Key point:** Pure functions can usually be tested directly through input/output assertions.

## 4. Table-Driven Tests

**Table-driven testing** uses a collection of input values and expected outputs to test the same function repeatedly.

In xUnit, `[Theory]` and `[InlineData]` support this approach.

### Example 1: Function

```csharp
static int Square(int number)
{
    return number * number;
}
```

### Table-driven test

```csharp
[Theory]
[InlineData(0, 0)]
[InlineData(1, 1)]
[InlineData(2, 4)]
[InlineData(3, 9)]
[InlineData(-4, 16)]
public void Square_ReturnsExpectedResult(
    int input,
    int expected)
{
    Assert.Equal(expected, Square(input));
}
```

### Test data

| Input | Expected |
|---|---|
| 0 | 0 |
| 1 | 1 |
| 2 | 4 |
| 3 | 9 |
| -4 | 16 |

All five cases use the same test method.

### Example 2: Predicate testing

```csharp
static bool IsEven(int number)
{
    return number % 2 == 0;
}
```

```csharp
[Theory]
[InlineData(2, true)]
[InlineData(3, false)]
[InlineData(0, true)]
[InlineData(-4, true)]
[InlineData(-5, false)]
public void IsEven_ReturnsExpectedResult(
    int number,
    bool expected)
{
    Assert.Equal(expected, IsEven(number));
}
```

### Benefits

| Benefit | Explanation |
|---|---|
| Less duplication | One test method covers many cases |
| Easy maintenance | New cases can be added as data |
| Readability | Inputs and expected outputs are visible |
| Consistency | Every case uses the same assertions |

**Key point:** Table-driven tests provide broad example-based coverage with minimal repeated test code.

## 5. Boundary Cases

**Boundary cases** test values at or near the limits of a function's valid input range.

Many defects occur at boundaries because conditions use operators such as:

```csharp
<
<=
>
>=
```

### Example 1: Age validation

```csharp
static bool IsValidAge(int age)
{
    return age >= 18 && age <= 60;
}
```

### Important boundary values

```text
17 → Invalid
18 → Valid
19 → Valid

59 → Valid
60 → Valid
61 → Invalid
```

### xUnit test

```csharp
[Theory]
[InlineData(17, false)]
[InlineData(18, true)]
[InlineData(19, true)]
[InlineData(59, true)]
[InlineData(60, true)]
[InlineData(61, false)]
public void IsValidAge_HandlesBoundaries(
    int age,
    bool expected)
{
    Assert.Equal(expected, IsValidAge(age));
}
```

### Example 2: Discount boundary

```csharp
static decimal CalculateDiscount(decimal amount)
{
    return amount >= 1000m
        ? amount * 0.10m
        : 0m;
}
```

Tests:

```csharp
[Theory]
[InlineData(999, 0)]
[InlineData(1000, 100)]
[InlineData(1001, 100.1)]
public void CalculateDiscount_HandlesThreshold(
    decimal amount,
    decimal expected)
{
    Assert.Equal(
        expected,
        CalculateDiscount(amount)
    );
}
```

### Boundary-testing pattern

For a threshold `N`, test:

```text
N - 1
N
N + 1
```

For a range, test both the lower and upper boundaries.

**Key point:** Boundary testing verifies behavior where valid and invalid input ranges meet.

## 6. Null Cases

**Null-case testing** verifies how functions behave when reference-type inputs are `null`.

A function should have an explicit null-handling contract.

Possible behaviors include:

- Rejecting `null`.
- Returning a default value.
- Returning an empty result.
- Representing missing data explicitly.

### Example 1: Reject null input

```csharp
static string Normalize(string input)
{
    ArgumentNullException.ThrowIfNull(input);

    return input.Trim().ToUpperInvariant();
}
```

### Test

```csharp
[Fact]
public void Normalize_Null_ThrowsException()
{
    Assert.Throws<ArgumentNullException>(
        () => Normalize(null!)
    );
}
```

### Example 2: Accept nullable input

```csharp
static string Normalize(string? input)
{
    return input?.Trim().ToUpperInvariant()
        ?? string.Empty;
}
```

Tests:

```csharp
[Theory]
[InlineData(null, "")]
[InlineData("", "")]
[InlineData(" hello ", "HELLO")]
public void Normalize_HandlesNullableInput(
    string? input,
    string expected)
{
    Assert.Equal(expected, Normalize(input));
}
```

### Example 3: Null collection

```csharp
static int CountItems(IEnumerable<int>? numbers)
{
    return numbers?.Count() ?? 0;
}
```

Test:

```csharp
[Fact]
public void CountItems_Null_ReturnsZero()
{
    Assert.Equal(0, CountItems(null));
}
```

### Important distinction

`null` and an empty collection are not necessarily equivalent.

```text
null → No collection supplied

[]   → Collection supplied with zero elements
```

Whether to treat them identically depends on the function's contract.

**Key point:** Null-case tests ensure missing references are handled intentionally rather than accidentally.

### Example 2: Empty aggregation

```csharp
static int SumNumbers(IEnumerable<int> numbers)
```

Test:

```csharp
[Fact]
```

### Example 3: Average of empty input

```csharp
static double AverageNumbers(
```

## 8. Invalid Inputs

**Invalid-input testing** verifies how a function responds when supplied values outside its accepted domain.

### Example 1: Factorial validation

```csharp
static long Factorial(int number)
{
    if (number < 0 || number > 20)
    {
        throw new ArgumentOutOfRangeException(
            nameof(number)
        );
    }

    long result = 1;

    for (int i = 2; i <= number; i++)
    {
        result *= i;
    }

    return result;
}
```

### Valid-input test

```csharp
[Fact]
public void Factorial_ValidInput_ReturnsResult()
{
    Assert.Equal(120, Factorial(5));
}
```

### Invalid-input test

```csharp
[Theory]
[InlineData(-1)]
[InlineData(21)]
public void Factorial_InvalidInput_Throws(int number)
{
    Assert.Throws<ArgumentOutOfRangeException>(
        () => Factorial(number)
    );
}
```

### Example 2: Invalid percentage

```csharp
static decimal ApplyDiscount(
    decimal price,
    decimal percentage)
{
    if (price < 0)
        throw new ArgumentOutOfRangeException(
            nameof(price)
        );

    if (percentage < 0 || percentage > 100)
        throw new ArgumentOutOfRangeException(
            nameof(percentage)
        );

    return price * (1 - percentage / 100);
}
```

Tests:

```csharp
[Theory]
[InlineData(-1, 10)]
[InlineData(100, -5)]
[InlineData(100, 120)]
public void ApplyDiscount_InvalidInput_Throws(
    decimal price,
    decimal percentage)
{
    Assert.Throws<ArgumentOutOfRangeException>(
        () => ApplyDiscount(price, percentage)
    );
}
```

### Invalid-input categories

| Category | Example |
|---|---|
| Negative values | Negative quantity |
| Out-of-range values | Percentage greater than 100 |
| Unsupported values | Invalid enum member |
| Invalid format | Non-numeric string |
| Missing required data | Empty required name |
| Invalid combinations | End date before start date |

**Key point:** Invalid-input tests verify that functions enforce their documented contracts.

## 9. Duplicate Inputs

**Duplicate-input testing** verifies whether repeated values are preserved, removed, grouped, or counted correctly.

The expected behavior depends on the operation.

### Example 1: Preserve duplicates

```csharp
static int[] DoubleNumbers(int[] numbers)
{
    return numbers
        .Select(x => x * 2)
        .ToArray();
}
```

Test:

```csharp
[Fact]
public void DoubleNumbers_PreservesDuplicates()
{
    int[] input = { 2, 2, 3 };

    int[] result = DoubleNumbers(input);

    Assert.Equal(
        new[] { 4, 4, 6 },
        result
    );
}
```

### Example 2: Remove duplicates

```csharp
static int[] RemoveDuplicates(int[] numbers)
{
    return numbers
        .Distinct()
        .ToArray();
}
```

Test:

```csharp
[Fact]
public void RemoveDuplicates_ReturnsUniqueValues()
{
    int[] input = { 1, 2, 2, 3, 3, 3 };

    int[] result = RemoveDuplicates(input);

    Assert.Equal(
        new[] { 1, 2, 3 },
        result
    );
}
```

For this example, the order matches LINQ-to-Objects behavior. If ordering is part of the function's contract, make it explicit, such as by adding `OrderBy()`.

### Example 3: Count duplicates

```csharp
static Dictionary<int, int> CountOccurrences(
    IEnumerable<int> numbers)
{
    return numbers
        .GroupBy(x => x)
        .ToDictionary(
            group => group.Key,
            group => group.Count()
        );
}
```

Test:

```csharp
[Fact]
public void CountOccurrences_CountsDuplicates()
{
    int[] input = { 1, 2, 2, 3, 3, 3 };

    var result = CountOccurrences(input);

    Assert.Equal(1, result[1]);
    Assert.Equal(2, result[2]);
    Assert.Equal(3, result[3]);
}
```

**Key point:** Duplicate-input tests confirm that repeated values are handled according to the intended semantics.

## 10. Property-Based Testing

**Property-based testing** verifies general rules that should hold for many inputs rather than testing only a few predetermined examples.

For example:

```text
For every integer x:

Double(x) = x × 2
```

A property-based testing framework can generate many inputs automatically.

### Example 1: Property of absolute value

For any integer other than `int.MinValue`, the result of `Math.Abs()` is nonnegative.

```csharp
static int Absolute(int number)
{
    return Math.Abs(number);
}
```

A property:

```text
Absolute(x) >= 0
```

### Example 2: Property-based test with FsCheck

FsCheck is a property-based testing library for .NET. The following example uses its xUnit integration.

```csharp
using FsCheck.Xunit;
using Xunit;

public class PropertyTests
{
    [Property]
    public bool Double_IsAlwaysEven(int number)
    {
        long result = (long)number * 2;

        return result % 2 == 0;
    }
}
```

The use of `long` avoids overflow when doubling an arbitrary `int`.

### Example 3: Reversal property

Reversing a sequence twice should produce the original sequence.

```csharp
[Property]
public bool ReverseTwice_ReturnsOriginal(int[] numbers)
{
    int[] reversedTwice = numbers
        .Reverse()
        .Reverse()
        .ToArray();

    return numbers.SequenceEqual(reversedTwice);
}
```

### Example 4: Sorting property

A sorted sequence must be nondecreasing.

```csharp
[Property]
public bool Sorting_ProducesOrderedValues(int[] numbers)
{
    int[] sorted = numbers
        .OrderBy(x => x)
        .ToArray();

    for (int i = 1; i < sorted.Length; i++)
    {
        if (sorted[i - 1] > sorted[i])
            return false;
    }

    return true;
}
```

### Example-based vs property-based testing

| Example-Based Testing | Property-Based Testing |
|---|---|
| Uses selected input values | Generates many input values |
| Checks expected examples | Checks general properties |
| Easy to understand | Can discover unexpected edge cases |
| Coverage depends on selected cases | Explores broader input ranges |

**Key point:** Property-based testing checks general rules across many automatically generated inputs.

## 11. Invariants

An **invariant** is a property that must remain true throughout an operation or after a transformation.

### Example 1: Sorting preserves element count

```csharp
static int[] SortNumbers(int[] numbers)
{
    return numbers
        .OrderBy(x => x)
        .ToArray();
}
```

Invariant:

```text
Input Count = Output Count
```

Test:

```csharp
[Fact]
public void Sorting_PreservesElementCount()
{
    int[] input = { 5, 2, 8, 1 };

    int[] result = SortNumbers(input);

    Assert.Equal(input.Length, result.Length);
}
```

### Example 2: Sorting preserves values

Sorting should change ordering, not the values themselves.

```csharp
[Fact]
public void Sorting_PreservesElements()
{
    int[] input = { 5, 2, 5, 1 };

    int[] result = SortNumbers(input);

    Assert.Equal(
        input.OrderBy(x => x),
        result
    );
}
```

### Example 3: Immutable state invariant

```csharp
public sealed record Account(decimal Balance);
```

```csharp
static Account Deposit(
    Account account,
    decimal amount)
{
    if (amount < 0)
        throw new ArgumentOutOfRangeException(
            nameof(amount)
        );

    return account with
    {
        Balance = account.Balance + amount
    };
}
```

Test:

```csharp
[Fact]
public void Deposit_DoesNotModifyOriginal()
{
    Account original = new(100m);

    Account updated = Deposit(original, 50m);

    Assert.Equal(100m, original.Balance);
    Assert.Equal(150m, updated.Balance);
}
```

### Common invariants

| Operation | Invariant |
|---|---|
| Sorting | Element count remains unchanged |
| Reversing | Element count remains unchanged |
| Mapping | One output per input for ordinary `Select()` |
| Deduplication | Output contains no duplicates |
| Immutable transformation | Original value remains unchanged |
| Validated state transition | State constraints remain satisfied |

**Key point:** Invariants describe properties that must remain true across transformations.

## 12. Identity Laws

An **identity law** states that applying an identity operation leaves a value unchanged.

### Mathematical identity

```text
Identity(x) = x
```

### Example 1: Identity function

```csharp
static T Identity<T>(T value)
{
    return value;
}
```

Usage:

```csharp
Console.WriteLine(Identity(10));
Console.WriteLine(Identity("Hello"));
```

**Output:**

```text
10
Hello
```

### Example 2: Test identity

```csharp
[Theory]
[InlineData(0)]
[InlineData(10)]
[InlineData(-5)]
public void Identity_ReturnsOriginalValue(int number)
{
    Assert.Equal(number, Identity(number));
}
```

### Example 3: LINQ identity projection

```csharp
int[] numbers = { 1, 2, 3 };

int[] result = numbers
    .Select(x => x)
    .ToArray();

Console.WriteLine(string.Join(", ", result));
```

**Output:**

```text
1, 2, 3
```

### Identity composition laws

For a function `f`:

```text
Identity(f(x)) = f(x)

f(Identity(x)) = f(x)
```

### Test

```csharp
[Fact]
public void Identity_CompositionPreservesResult()
{
    Func<int, int> doubleValue = x => x * 2;

    int input = 5;

    Assert.Equal(
        doubleValue(input),
        Identity(doubleValue(input))
    );

    Assert.Equal(
        doubleValue(input),
        doubleValue(Identity(input))
    );
}
```

**Key point:** Identity laws verify that identity transformations do not change observable results.

## 13. Associativity Laws

**Associativity** describes whether changing the grouping of operations preserves the result.

For an associative operation `⊕`:

```text
(a ⊕ b) ⊕ c = a ⊕ (b ⊕ c)
```

### Example 1: Integer addition

Mathematically:

```text
(2 + 3) + 4 = 2 + (3 + 4)

9 = 9
```

C#:

```csharp
int left = (2 + 3) + 4;

int right = 2 + (3 + 4);

Console.WriteLine(left == right);
```

**Output:**

```text
True
```

### Example 2: Test associativity

```csharp
[Theory]
[InlineData(1, 2, 3)]
[InlineData(10, 20, 30)]
[InlineData(-5, 10, 2)]
public void Addition_IsAssociativeForTheseValues(
    int a,
    int b,
    int c)
{
    long left = ((long)a + b) + c;

    long right = (long)a + (b + (long)c);

    Assert.Equal(left, right);
}
```

Using `long` ensures that sums of three `int` values fit without overflow.

### Example 3: String concatenation

```csharp
string a = "A";
string b = "B";
string c = "C";

string left = (a + b) + c;

string right = a + (b + c);

Console.WriteLine(left);
Console.WriteLine(right);
```

**Output:**

```text
ABC
ABC
```

### Example 4: Non-associative operation

Subtraction is not associative.

```csharp
int left = (10 - 5) - 2;

int right = 10 - (5 - 2);

Console.WriteLine(left);
Console.WriteLine(right);
```

**Output:**

```text
3
7
```

### Important consideration

Floating-point addition is not generally associative because rounding can change results.

Associativity tests must account for the actual numeric type and its semantics.

**Key point:** Associativity laws verify whether operations can be regrouped without changing their results.

## 14. Composition Laws

**Composition laws** describe properties of combining functions.

Function composition should preserve expected relationships between the original functions.

### Example 1: Define composition

```csharp
static Func<TInput, TOutput> Compose<TInput, TMiddle, TOutput>(
    Func<TInput, TMiddle> first,
    Func<TMiddle, TOutput> second)
{
    return input => second(first(input));
}
```

### Example 2: Define functions

```csharp
Func<int, int> addTwo = x => x + 2;

Func<int, int> multiplyThree = x => x * 3;

Func<int, string> format = x => $"Value: {x}";
```

### Example 3: Composition associativity

```csharp
var left = Compose(
    Compose(addTwo, multiplyThree),
    format
);

var right = Compose(
    addTwo,
    Compose(multiplyThree, format)
);

Console.WriteLine(left(5));
Console.WriteLine(right(5));
```

**Output:**

```text
Value: 21
Value: 21
```

### Mathematical law

```text
(h ∘ g) ∘ f = h ∘ (g ∘ f)
```

This means grouping function composition differently should not change the result.

### Test

```csharp
[Fact]
public void FunctionComposition_IsAssociative()
{
    Func<int, int> f = x => x + 2;
    Func<int, int> g = x => x * 3;
    Func<int, string> h = x => $"Result: {x}";

    var left = Compose(Compose(f, g), h);
    var right = Compose(f, Compose(g, h));

    Assert.Equal(left(5), right(5));
}
```

### Identity law for composition

```text
Compose(Identity, f) = f

Compose(f, Identity) = f
```

For pure functions, these laws describe equivalent results.

**Key point:** Composition-law tests verify that combining functions preserves expected mathematical relationships.

## 15. Testing Pipelines

**Pipeline testing** verifies that a sequence of connected transformations produces the correct final result.

A pipeline may include filtering, projection, ordering, and aggregation.

### Example 1: Define pipeline

```csharp
static int[] ProcessNumbers(
    IEnumerable<int> numbers)
{
    return numbers
        .Where(x => x > 0)
        .Select(x => x * 2)
        .OrderBy(x => x)
        .ToArray();
}
```

### Example 2: Test complete pipeline

```csharp
[Fact]
public void ProcessNumbers_ReturnsExpectedResult()
{
    int[] input = { 5, -2, 3, 1 };

    int[] result = ProcessNumbers(input);

    Assert.Equal(
        new[] { 2, 6, 10 },
        result
    );
}
```

### Execution flow

```text
Input:
5, -2, 3, 1
      │
      ▼
Filter Positive
5, 3, 1
      │
      ▼
Double
10, 6, 2
      │
      ▼
Sort
2, 6, 10
```

### Example 3: Test empty pipeline input

```csharp
[Fact]
public void ProcessNumbers_EmptyInput_ReturnsEmpty()
{
    int[] result =
        ProcessNumbers(Array.Empty<int>());

    Assert.Empty(result);
}
```

### Example 4: Test all-negative input

```csharp
[Fact]
public void ProcessNumbers_AllNegative_ReturnsEmpty()
{
    int[] input = { -1, -2, -3 };

    int[] result = ProcessNumbers(input);

    Assert.Empty(result);
}
```

### Pipeline-testing strategy

1. Test individual transformations.
2. Test filtering behavior.
3. Test operation ordering.
4. Test the complete output.
5. Test empty and invalid inputs.
6. Test whether the original data remains unchanged when required.

**Key point:** Pipeline tests verify that individual stages work correctly when composed.

## 16. Testing without I/O

**Testing without I/O** means verifying core logic without performing file, database, console, or network operations.

This is possible when the computation is separated from its external dependencies.

### Example 1: Function mixed with file I/O

```csharp
static int CountWordsInFile(string path)
{
    string text = File.ReadAllText(path);

    return text.Split(
        ' ',
        StringSplitOptions.RemoveEmptyEntries
    ).Length;
}
```

This function requires an actual file.

### Example 2: Separate the computation

```csharp
static int CountWords(string text)
{
    ArgumentNullException.ThrowIfNull(text);

    return text.Split(
        ' ',
        StringSplitOptions.RemoveEmptyEntries
    ).Length;
}
```

### Test without a file

```csharp
[Fact]
public void CountWords_ReturnsCorrectCount()
{
    int result = CountWords(
        "C# functional programming"
    );

    Assert.Equal(3, result);
}
```

### Example 3: Keep I/O at the boundary

```csharp
string text = File.ReadAllText("input.txt");

int count = CountWords(text);

Console.WriteLine(count);
```

### Architecture

```text
FILE SYSTEM
     │
     ▼
READ TEXT
     │
     ▼
PURE FUNCTION
CountWords(text)
     │
     ▼
RESULT
```

The pure function can be tested without accessing the file system.

### Benefits

| Benefit | Explanation |
|---|---|
| Speed | No slow external operations |
| Reliability | Fewer environmental failures |
| Isolation | Tests focus on calculation |
| Repeatability | Fixed input produces fixed output |
| Simplicity | No test files or database setup required |

**Key point:** Separate external I/O from core logic so the logic can be tested independently.

## 17. Testing Failure Cases

**Failure-case testing** verifies how a function behaves when an operation cannot succeed.

Failure handling may use exceptions, nullable values, or explicit result objects.

### Example 1: Division failure

```csharp
static int Divide(int a, int b)
{
    if (b == 0)
        throw new DivideByZeroException();

    return a / b;
}
```

### Test exception

```csharp
[Fact]
public void Divide_ByZero_Throws()
{
    Assert.Throws<DivideByZeroException>(
        () => Divide(10, 0)
    );
}
```

### Example 2: Explicit failure result

```csharp
public sealed record CalculationResult(
    bool Success,
    int Value,
    string? Error
);
```

```csharp
static CalculationResult SafeDivide(int a, int b)
{
    if (b == 0)
    {
        return new(
            false,
            0,
            "Division by zero"
        );
    }

    return new(
        true,
        a / b,
        null
    );
}
```

### Test failure result

```csharp
[Fact]
public void SafeDivide_ByZero_ReturnsFailure()
{
    CalculationResult result =
        SafeDivide(10, 0);

    Assert.False(result.Success);

    Assert.Equal(
        "Division by zero",
        result.Error
    );
}
```

### Test success result

```csharp
[Fact]
public void SafeDivide_ValidInput_ReturnsSuccess()
{
    CalculationResult result =
        SafeDivide(10, 2);

    Assert.True(result.Success);

    Assert.Equal(5, result.Value);
}
```

### Common failure cases

| Failure | Expected Test |
|---|---|
| Division by zero | Exception or explicit failure |
| Invalid input | Validation error |
| Missing value | Nullable or failure result |
| Unsupported operation | Appropriate exception |
| Overflow | Checked arithmetic behavior |
| External dependency failure | Controlled error handling |

**Key point:** Failure-case tests ensure that unsuccessful operations produce predictable, documented behavior.

## 18. Testing Side-Effect Boundaries

**Side-effect boundary testing** verifies that code interacts correctly with external services while keeping core calculations independent.

Side-effect boundaries may include:

- Database repositories.
- File-system services.
- HTTP clients.
- Logging services.
- Console output.

### Example 1: Define an effect interface

```csharp
public interface IMessageWriter
{
    void Write(string message);
}
```

### Example 2: Real implementation

```csharp
public sealed class ConsoleMessageWriter
    : IMessageWriter
{
    public void Write(string message)
    {
        Console.WriteLine(message);
    }
}
```

### Example 3: Application service

```csharp
public sealed class GreetingService
{
    private readonly IMessageWriter _writer;

    public GreetingService(IMessageWriter writer)
    {
        _writer = writer;
    }

    public void Greet(string name)
    {
        string message = $"Hello, {name}";

        _writer.Write(message);
    }
}
```

The service depends on an abstraction rather than directly using the console.

### Example 4: Fake implementation for testing

```csharp
public sealed class FakeMessageWriter
    : IMessageWriter
{
    public List<string> Messages { get; } = new();

    public void Write(string message)
    {
        Messages.Add(message);
    }
}
```

### Example 5: Test the boundary

```csharp
[Fact]
public void Greet_WritesExpectedMessage()
{
    var writer = new FakeMessageWriter();

    var service = new GreetingService(writer);

    service.Greet("Rahul");

    Assert.Single(writer.Messages);

    Assert.Equal(
        "Hello, Rahul",
        writer.Messages[0]
    );
}
```

**Test result:**

```text
Passed
```

No console output is required.

### Example 6: Verify multiple interactions

```csharp
[Fact]
public void Greet_MultipleCalls_WriteMultipleMessages()
{
    var writer = new FakeMessageWriter();

    var service = new GreetingService(writer);

    service.Greet("Amit");
    service.Greet("Priya");

    Assert.Equal(2, writer.Messages.Count);

    Assert.Equal(
        "Hello, Amit",
        writer.Messages[0]
    );

    Assert.Equal(
        "Hello, Priya",
        writer.Messages[1]
    );
}
```

### Architecture

```text
                  TEST
                    │
                    ▼
             GREETING SERVICE
                    │
                    ▼
             IMessageWriter
                    │
          ┌─────────┴─────────┐
          │                   │
          ▼                   ▼
   REAL IMPLEMENTATION   FAKE IMPLEMENTATION
          │                   │
          ▼                   ▼
       CONSOLE           MEMORY LIST
```

### What boundary tests verify

| Concern | Verification |
|---|---|
| Correct output | Expected message or data is sent |
| Call count | Dependency is invoked the expected number of times |
| Call order | Operations occur in the required sequence |
| Failure handling | Dependency failures are handled correctly |
| Isolation | Tests do not require real external resources |

### Important distinction

A fake implementation verifies the application's interaction with the abstraction.

It does not prove that the real console, database, file system, or network integration works correctly.

Those real integrations require separate integration tests.

**Key point:** Side-effect boundary tests verify external interactions using controlled dependencies.
