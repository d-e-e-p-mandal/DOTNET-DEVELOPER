# 09.08 — MODELING ABSENCE & FAILURE

**Chapter:** 09 — Functional C#  
**Total Syllabus Points:** 19  
**Language:** C#  
**Primary namespaces:** `System`, `System.Collections.Generic`

In functional programming, **absence** and **failure** are treated as possible outcomes of computations.

A function does not always produce a usable value. Sometimes:

- The requested value does not exist.
- The input is invalid.
- A conversion fails.
- A business rule is violated.
- An operation cannot be completed.

Instead of hiding these possibilities, functional programming encourages representing them explicitly through types and return values.

For example:

```text
Operation
    │
    ├── Value exists
    │
    ├── Value absent
    │
    ├── Operation successful
    │
    └── Operation failed
```

C# supports these ideas through nullable types, Try-pattern methods, and custom or library-provided `Option`, `Result`, and `Either` types.

**Important:** `Option<T>`, `Result<T>`, and `Either<L,R>` are concepts used by functional programming libraries and custom implementations. They are not general-purpose built-in types in the .NET base class library.

---

## 1. Absence as Data

**Absence as data** means representing the possibility that a value does not exist as part of a function's return type.

### Traditional approach

```csharp
static string? FindName(int id)
{
    if (id == 1)
        return "Amit";

    return null;
}
```

Usage:

```csharp
string? name = FindName(2);

Console.WriteLine(name ?? "Not Found");
```

**Output:**

```text
Not Found
```

Here, `null` represents absence.

### Example 2: Absence with nullable value types

```csharp
static int? FindScore(int studentId)
{
    if (studentId == 1)
        return 90;

    return null;
}

int? score = FindScore(2);

Console.WriteLine(
    score.HasValue ? score.Value : "No Score"
);
```

**Output:**

```text
No Score
```

### Example 3: Absence with a custom type

```csharp
record Option<T>(
    bool HasValue,
    T? Value
);
```

Usage:

```csharp
Option<int> result = new(
    HasValue: false,
    Value: default
);

Console.WriteLine(result.HasValue);
```

**Output:**

```text
False
```

This simple representation demonstrates the concept, but it is not a fully protected `Option<T>` implementation because callers can construct inconsistent states.

### Why model absence explicitly?

Consider:

```csharp
static int GetAge()
{
    return 0;
}
```

Does `0` mean:

- The person's age is zero?
- The age is unknown?
- The age was not found?

The return type does not explain the meaning.

A nullable return type makes the distinction clearer:

```csharp
static int? GetAge()
{
    return null;
}
```

**Key point:** Absence should be represented explicitly rather than confused with an ordinary value.

## 2. Failure as Data

**Failure as data** means representing an unsuccessful computation as a return value.

Instead of always throwing an exception, a function can return information describing its failure.

### Example 1: Return success status

```csharp
static bool IsValidAge(int age)
{
    return age >= 18;
}

Console.WriteLine(IsValidAge(25));
Console.WriteLine(IsValidAge(15));
```

**Output:**

```text
True
False
```

This communicates success or failure, but not the reason for failure.

### Example 2: Return an error message

```csharp
record ValidationResult(
    bool IsSuccess,
    string? Error
);

static ValidationResult ValidateAge(int age)
{
    if (age < 18)
    {
        return new(
            false,
            "Age must be at least 18"
        );
    }

    return new(true, null);
}

ValidationResult result = ValidateAge(15);

Console.WriteLine(result.IsSuccess);
Console.WriteLine(result.Error);
```

**Output:**

```text
False
Age must be at least 18
```

### Example 3: Return success or failure with a value

```csharp
record Result<T>(
    bool IsSuccess,
    T? Value,
    string? Error
);

static Result<int> Divide(int a, int b)
{
    if (b == 0)
    {
        return new(
            false,
            default,
            "Division by zero"
        );
    }

    return new(
        true,
        a / b,
        null
    );
}

Result<int> result = Divide(10, 0);

Console.WriteLine(result.IsSuccess);
Console.WriteLine(result.Error);
```

**Output:**

```text
False
Division by zero
```

### Difference between absence and failure

| Absence | Failure |
|---|---|
| A value does not exist | An operation was unsuccessful |
| May be a normal outcome | Usually indicates an error condition |
| Example: employee not found | Example: invalid employee ID |
| Often modeled with `Option<T>` | Often modeled with `Result<T>` |

**Key point:** Failure as data makes unsuccessful outcomes explicit and allows callers to handle them through ordinary control flow.

## 3. Nullable Value Types

Nullable value types allow a value type to represent either a value or `null`.

### Syntax

```csharp
int?
double?
decimal?
bool?
DateTime?
```

The syntax:

```csharp
int?
```

is shorthand for:

```csharp
Nullable<int>
```

### Example 1: Nullable integer

```csharp
int? age = null;

Console.WriteLine(age.HasValue);
```

**Output:**

```text
False
```

### Example 2: Nullable with a value

```csharp
int? age = 25;

Console.WriteLine(age.HasValue);
Console.WriteLine(age.Value);
```

**Output:**

```text
True
25
```

Accessing `.Value` when no value exists throws `InvalidOperationException`.

### Example 3: GetValueOrDefault

```csharp
int? age = null;

Console.WriteLine(age.GetValueOrDefault());
Console.WriteLine(age.GetValueOrDefault(18));
```

**Output:**

```text
0
18
```

### Example 4: Null-coalescing operator

```csharp
int? score = null;

int finalScore = score ?? 0;

Console.WriteLine(finalScore);
```

**Output:**

```text
0
```

### Example 5: Nullable arithmetic

```csharp
int? a = 10;
int? b = null;

int? result = a + b;

Console.WriteLine(result.HasValue);
```

**Output:**

```text
False
```

For lifted nullable arithmetic, an absent operand generally produces an absent result.

### Example 6: Nullable return type

```csharp
static int? FindNumber(int[] numbers)
{
    foreach (int number in numbers)
    {
        if (number > 100)
            return number;
    }

    return null;
}

int? result = FindNumber(
    new[] { 10, 20, 30 }
);

Console.WriteLine(result ?? -1);
```

**Output:**

```text
-1
```

**Key point:** `Nullable<T>` represents an optional value for non-nullable value types.

## 4. Nullable Reference Types

Nullable reference types allow developers to express whether a reference is expected to contain `null`.

This feature is primarily enforced through compiler analysis and warnings.

### Enable nullable reference types

In a C# file:

```csharp
#nullable enable
```

Or in a project file:

```xml
<Nullable>enable</Nullable>
```

### Example 1: Non-nullable reference

```csharp
#nullable enable

string name = "Amit";

Console.WriteLine(name.Length);
```

**Output:**

```text
4
```

### Example 2: Nullable reference

```csharp
#nullable enable

string? name = null;

Console.WriteLine(name ?? "Unknown");
```

**Output:**

```text
Unknown
```

### Example 3: Null checking

```csharp
#nullable enable

string? name = null;

if (name is not null)
{
    Console.WriteLine(name.Length);
}
else
{
    Console.WriteLine("Name is absent");
}
```

**Output:**

```text
Name is absent
```

### Example 4: Null-conditional operator

```csharp
#nullable enable

string? name = null;

int? length = name?.Length;

Console.WriteLine(length ?? 0);
```

**Output:**

```text
0
```

### Example 5: Nullable method return

```csharp
#nullable enable

static string? FindEmployee(int id)
{
    return id == 1 ? "Amit" : null;
}

string? employee = FindEmployee(2);

Console.WriteLine(employee ?? "Not Found");
```

**Output:**

```text
Not Found
```

### Nullable value vs reference types

| Nullable Value Type | Nullable Reference Type |
|---|---|
| `int?` | `string?` |
| Uses `Nullable<T>` | Uses nullable annotations and analysis |
| Has `HasValue` | Does not have `HasValue` |
| Has `.Value` | Accessed through the reference |
| Runtime representation changes | Primarily compiler-level nullability information |

**Key point:** Nullable reference types help detect potential null-reference problems during compilation, but they do not guarantee that a reference can never be null at runtime.

## 5. Try-Pattern APIs

The **Try pattern** represents an operation that may fail without throwing an exception for an ordinary unsuccessful outcome.

A Try-pattern method commonly:

1. Returns `bool`.
2. Provides the successful value through an `out` parameter.

### Example 1: int.TryParse

```csharp
string input = "123";

bool success = int.TryParse(
    input,
    out int number
);

Console.WriteLine(success);
Console.WriteLine(number);
```

**Output:**

```text
True
123
```

### Example 2: Failed conversion

```csharp
string input = "ABC";

bool success = int.TryParse(
    input,
    out int number
);

Console.WriteLine(success);
Console.WriteLine(number);
```

**Output:**

```text
False
0
```

The output parameter receives its default value when parsing fails.

### Example 3: Dictionary.TryGetValue

```csharp
Dictionary<int, string> employees = new()
{
    [1] = "Amit",
    [2] = "Rahul"
};

bool found = employees.TryGetValue(
    1,
    out string? name
);

Console.WriteLine(found);
Console.WriteLine(name);
```

**Output:**

```text
True
Amit
```

### Example 4: DateTime.TryParse

```csharp
using System.Globalization;

string input = "2026-10-19";

bool success = DateTime.TryParseExact(
    input,
    "yyyy-MM-dd",
    CultureInfo.InvariantCulture,
    DateTimeStyles.None,
    out DateTime date
);

Console.WriteLine(success);
Console.WriteLine(
    date.ToString(
        "yyyy-MM-dd",
        CultureInfo.InvariantCulture
    )
);
```

**Output:**

```text
True
2026-10-19
```

### Example 5: Custom Try method

```csharp
static bool TryDivide(
    int numerator,
    int denominator,
    out int result
)
{
    if (denominator == 0)
    {
        result = default;
        return false;
    }

    result = numerator / denominator;
    return true;
}

if (TryDivide(20, 4, out int answer))
{
    Console.WriteLine(answer);
}
else
{
    Console.WriteLine("Division failed");
}
```

**Output:**

```text
5
```

**Key point:** Try-pattern APIs represent expected failure through a boolean result and an output parameter.

## 6. bool + out Patterns

The `bool + out` pattern is the underlying structure commonly used by Try-pattern APIs.

### General structure

```csharp
static bool TryOperation(
    InputType input,
    out OutputType result
)
{
    // Assign result on every return path.
    // Return true for success.
    // Return false for failure.
}
```

### Example 1: Custom employee lookup

```csharp
static bool TryFindEmployee(
    int id,
    out string? name
)
{
    if (id == 1)
    {
        name = "Amit";
        return true;
    }

    name = null;
    return false;
}

bool found = TryFindEmployee(
    2,
    out string? employee
);

Console.WriteLine(found);
Console.WriteLine(employee ?? "Not Found");
```

**Output:**

```text
False
Not Found
```

### Example 2: Out variable declaration

```csharp
bool success = int.TryParse(
    "100",
    out int value
);

Console.WriteLine(value);
```

**Output:**

```text
100
```

### Example 3: Discard unused output

```csharp
bool valid = int.TryParse(
    "250",
    out _
);

Console.WriteLine(valid);
```

**Output:**

```text
True
```

### Example 4: Conditional use

```csharp
string input = "75";

if (int.TryParse(input, out int number))
{
    Console.WriteLine(number * 2);
}
else
{
    Console.WriteLine("Invalid input");
}
```

**Output:**

```text
150
```

### Advantages and limitations

| Advantage | Limitation |
|---|---|
| Avoids exceptions for expected failures | Typically returns limited error information |
| Efficient for common parsing and lookup operations | Requires an `out` parameter |
| Familiar C# convention | Less convenient for function composition |
| Supports direct success checks | Cannot be directly represented as an ordinary `Func<T,TResult>` with the `out` parameter |

**Key point:** The `bool + out` pattern is practical for ordinary C# APIs, while functional programming often favors returning a single value that represents both possible outcomes.

## 7. Option / Maybe Concept

An **Option** or **Maybe** type represents a value that may or may not exist.

Conceptually:

```text
Option<T>
    │
    ├── Some(T)
    │
    └── None
```

An Option type is useful when absence is a normal, expected outcome.

### Example 1: Basic Option implementation

The following example uses a small custom `Option<T>` type.

```csharp
public readonly record struct Option<T>(
    bool HasValue,
    T? Value
);
```

Usage:

```csharp
Option<int> first = new(true, 100);
Option<int> second = new(false, default);

Console.WriteLine(first.HasValue);
Console.WriteLine(second.HasValue);
```

**Output:**

```text
True
False
```

This simplified type illustrates the concept but does not enforce every Option invariant.

### Example 2: Return an Option

```csharp
public readonly record struct Option<T>(
    bool HasValue,
    T? Value
);

static Option<int> FindScore(int id)
{
    if (id == 1)
        return new(true, 90);

    return new(false, default);
}

Option<int> result = FindScore(2);

Console.WriteLine(
    result.HasValue
        ? result.Value
        : "No Score"
);
```

**Output:**

```text
No Score
```

### Example 3: Option with a reference type

```csharp
public readonly record struct Option<T>(
    bool HasValue,
    T? Value
);

static Option<string> FindName(int id)
{
    return id == 1
        ? new(true, "Amit")
        : new(false, default);
}

Option<string> result = FindName(1);

Console.WriteLine(result.Value);
```

**Output:**

```text
Amit
```

### Option vs nullable

| Option / Maybe | Nullable |
|---|---|
| Explicit functional abstraction | Built-in C# nullability mechanism |
| Represents Some or None | Represents value or null |
| Can expose Map and Bind operations | Supports null operators and checks |
| May be implemented as a custom or library type | Supported by the language and runtime |
| Can encode absence in a dedicated API | Uses nullable values or references |

**Key point:** Option represents optional data as an explicit type with present and absent cases.

## 8. Some / None Concept

**Some** represents the presence of a value.

**None** represents the absence of a value.

### Conceptual representation

```text
Some(100)
    │
    └── Value exists

None
    │
    └── Value absent
```

### Example 1: Some case

```csharp
public abstract record Option<T>;

public sealed record Some<T>(T Value)
    : Option<T>;

public sealed record None<T>()
    : Option<T>;
```

Usage:

```csharp
Option<int> result = new Some<int>(100);

if (result is Some<int> some)
{
    Console.WriteLine(some.Value);
}
```

**Output:**

```text
100
```

### Example 2: None case

Using the same type definitions:

```csharp
Option<int> result = new None<int>();

if (result is None<int>)
{
    Console.WriteLine("No value");
}
```

**Output:**

```text
No value
```

### Example 3: Pattern matching

```csharp
public abstract record Option<T>;

public sealed record Some<T>(T Value)
    : Option<T>;

public sealed record None<T>()
    : Option<T>;

static string Describe(Option<int> option)
{
    return option switch
    {
        Some<int> some => $"Value: {some.Value}",
        None<int> => "No value",
        _ => throw new InvalidOperationException()
    };
}

Console.WriteLine(
    Describe(new Some<int>(50))
);

Console.WriteLine(
    Describe(new None<int>())
);
```

**Output:**

```text
Value: 50
No value
```

### Example 4: Returning Some or None

```csharp
public abstract record Option<T>;

public sealed record Some<T>(T Value)
    : Option<T>;

public sealed record None<T>()
    : Option<T>;

static Option<int> FindPositive(int number)
{
    return number > 0
        ? new Some<int>(number)
        : new None<int>();
}

Option<int> result = FindPositive(-5);

Console.WriteLine(
    result is None<int>
);
```

**Output:**

```text
True
```

**Key point:** Some and None make the two possible states of an optional value explicit.

## 9. Result Concept

A **Result** type represents a computation that can succeed or fail.

Unlike Option, Result usually carries information about why an operation failed.

### Conceptual representation

```text
Result<T>
    │
    ├── Success(T)
    │
    └── Failure(Error)
```

### Example 1: Simple Result

```csharp
public abstract record Result<T>;

public sealed record Success<T>(T Value)
    : Result<T>;

public sealed record Failure<T>(string Error)
    : Result<T>;
```

### Example 2: Successful result

Using the preceding definitions:

```csharp
Result<int> result = new Success<int>(100);

if (result is Success<int> success)
{
    Console.WriteLine(success.Value);
}
```

**Output:**

```text
100
```

### Example 3: Failed result

```csharp
Result<int> result =
    new Failure<int>("Invalid input");

if (result is Failure<int> failure)
{
    Console.WriteLine(failure.Error);
}
```

**Output:**

```text
Invalid input
```

### Example 4: Division with Result

```csharp
public abstract record Result<T>;

public sealed record Success<T>(T Value)
    : Result<T>;

public sealed record Failure<T>(string Error)
    : Result<T>;

static Result<int> Divide(int a, int b)
{
    if (b == 0)
    {
        return new Failure<int>(
            "Cannot divide by zero"
        );
    }

    return new Success<int>(a / b);
}

Result<int> result = Divide(20, 0);

string message = result switch
{
    Success<int> success =>
        $"Result: {success.Value}",

    Failure<int> failure =>
        failure.Error,

    _ => throw new InvalidOperationException()
};

Console.WriteLine(message);
```

**Output:**

```text
Cannot divide by zero
```

### Option vs Result

| Option | Result |
|---|---|
| Represents presence or absence | Represents success or failure |
| Some contains a value | Success contains a value |
| None represents absence | Failure contains error information |
| Useful for lookup operations | Useful for validation and processing |
| Does not inherently explain absence | Can explain failure |

**Key point:** Result represents successful and unsuccessful computations as explicit values.

## 10. Either Concept

**Either** represents a value that can be one of two possible types.

A common convention is:

```text
Either<L, R>
    │
    ├── Left(L)
    │
    └── Right(R)
```

In many functional programming libraries:

- `Left` represents an error.
- `Right` represents success.

However, this is a convention rather than an inherent requirement of the type.

### Example 1: Either implementation

```csharp
public abstract record Either<L, R>;

public sealed record Left<L, R>(L Value)
    : Either<L, R>;

public sealed record Right<L, R>(R Value)
    : Either<L, R>;
```

### Example 2: Right value

```csharp
Either<string, int> result =
    new Right<string, int>(100);

if (result is Right<string, int> right)
{
    Console.WriteLine(right.Value);
}
```

**Output:**

```text
100
```

### Example 3: Left value

```csharp
Either<string, int> result =
    new Left<string, int>("Invalid input");

if (result is Left<string, int> left)
{
    Console.WriteLine(left.Value);
}
```

**Output:**

```text
Invalid input
```

### Example 4: Parsing with Either

```csharp
public abstract record Either<L, R>;

public sealed record Left<L, R>(L Value)
    : Either<L, R>;

public sealed record Right<L, R>(R Value)
    : Either<L, R>;

static Either<string, int> ParseNumber(
    string input
)
{
    if (int.TryParse(input, out int number))
    {
        return new Right<string, int>(number);
    }

    return new Left<string, int>(
        "Invalid number"
    );
}

Either<string, int> result =
    ParseNumber("ABC");

Console.WriteLine(
    result is Left<string, int>
);
```

**Output:**

```text
True
```

### Result vs Either

| Result | Either |
|---|---|
| Represents success or failure | Represents one of two possible types |
| Usually has Success and Failure | Usually has Left and Right |
| Error type may be fixed or generic | Both types are commonly generic |
| Expresses operation outcomes | General two-case representation |

**Key point:** Either provides a general way to represent two alternative outcomes with different types.

## 11. Success Case

### Example 1: Success value

```csharp
record Result<T>(

Result<int> result = new(

    100,

);

Console.WriteLine(result.IsSuccess);
```

```text
True
100
```

```csharp
record Result<T>(

static Result<int> ParseNumber(string input)
{

Result<int> result = ParseNumber("250");
```

## 12. Failure Case

The **failure case** represents an operation that could not complete successfully.

It usually contains information describing the error.

### Example 1: Failure value

```csharp
record Result<T>(
    bool IsSuccess,
    T? Value,

Result<int> result = new(
    false,
    default,
    "Invalid input"
);

Console.WriteLine(result.IsSuccess);
Console.WriteLine(result.Error);
```

**Output:**

```text
False
Invalid input
```

### Example 2: Validation failure

```csharp
public abstract record Result<T>;

public sealed record Success<T>(T Value)

public sealed record Failure<T>(string Error)
    : Result<T>;

static Result<int> ValidateAge(int age)
{
    if (age < 18)
    {
        return new Failure<int>(
            "Age must be at least 18"
        );

    return new Success<int>(age);
}

Result<int> result = ValidateAge(15);

if (result is Failure<int> failure)
{
    Console.WriteLine(failure.Error);
}
```

**Output:**

```text

```

### Example 3: Different failure reasons

```csharp
public abstract record Result<T>;

public sealed record Success<T>(T Value)
    : Result<T>;

public sealed record Failure<T>(string Error)
    : Result<T>;

static Result<int> ValidateScore(int score)
{
    if (score < 0)
        return new Failure<int>(
            "Score cannot be negative"
        );

    if (score > 100)
        return new Failure<int>(
            "Score cannot exceed 100"
        );

    return new Success<int>(score);
}

Result<int> result = ValidateScore(150);

Console.WriteLine(
    ((Failure<int>)result).Error
);
```

**Output:**

```text
Score cannot exceed 100
```

### Failure case characteristics

| Property | Meaning |
|---|---|
| Failure state | Computation unsuccessful |
| Error message | Describes the failure |
| Error code | Can identify a failure category |
| Error details | Can provide additional information |
| Caller responsibility | Handle or propagate the failure |

**Key point:** A failure case communicates unsuccessful outcomes without requiring exceptions for every expected error.

## 13. Mapping Successful Values

**Mapping successful values** means applying a transformation only when a Result contains a successful value.

If the Result contains a failure, the failure is preserved.

### Concept

```text
Success(10)
    │
    ▼
Map(x => x * 2)
    │
    ▼
Success(20)
```

But:

```text
Failure("Error")
    │
    ▼
Map(x => x * 2)
    │
    ▼
Failure("Error")
```

### Example 1: Generic Map implementation

```csharp
public abstract record Result<T>;

public sealed record Success<T>(T Value)
    : Result<T>;

public sealed record Failure<T>(string Error)
    : Result<T>;

static Result<R> Map<T, R>(
    Result<T> result,
    Func<T, R> selector
)
{
    return result switch
    {
        Success<T> success =>
            new Success<R>(selector(success.Value)),

        Failure<T> failure =>
            new Failure<R>(failure.Error),

        _ => throw new InvalidOperationException()
    };
}
```

### Example 2: Map a successful value

Using the previous definitions:

```csharp
Result<int> original =
    new Success<int>(10);

Result<int> updated = Map(
    original,
    x => x * 2
);

Console.WriteLine(
    ((Success<int>)updated).Value
);
```

**Output:**

```text
20
```

### Example 3: Map a failed result

```csharp
Result<int> original =
    new Failure<int>("Invalid number");

Result<int> updated = Map(
    original,
    x => x * 2
);

Console.WriteLine(
    ((Failure<int>)updated).Error
);
```

**Output:**

```text
Invalid number
```

The transformation is skipped.

### Example 4: Map to a different type

```csharp
Result<int> original =
    new Success<int>(100);

Result<string> updated = Map(
    original,
    number => $"Value: {number}"
);

Console.WriteLine(
    ((Success<string>)updated).Value
);
```

**Output:**

```text
Value: 100
```

### Map behavior

| Input | Transformation | Output |
|---|---|---|
| `Success(10)` | Multiply by 2 | `Success(20)` |
| `Success(5)` | Convert to string | `Success("5")` |
| `Failure("Error")` | Multiply by 2 | `Failure("Error")` |

**Key point:** Map transforms successful values while preserving failures.

## 14. Binding Successful Values

**Binding successful values** means applying a function that itself returns another Result.

This is different from Map.

### Map

```text
T → R
```

### Bind

```text
T → Result<R>
```

Bind avoids producing nested Result structures.

### Example 1: Generic Bind implementation

```csharp
public abstract record Result<T>;

public sealed record Success<T>(T Value)
    : Result<T>;

public sealed record Failure<T>(string Error)
    : Result<T>;

static Result<R> Bind<T, R>(
    Result<T> result,
    Func<T, Result<R>> next
)
{
    return result switch
    {
        Success<T> success =>
            next(success.Value),

        Failure<T> failure =>
            new Failure<R>(failure.Error),

        _ => throw new InvalidOperationException()
    };
}
```

### Example 2: Bind successful values

```csharp
static Result<int> DoublePositive(int number)
{
    if (number <= 0)
    {
        return new Failure<int>(
            "Number must be positive"
        );
    }

    return new Success<int>(number * 2);
}

Result<int> original =
    new Success<int>(10);

Result<int> updated = Bind(
    original,
    DoublePositive
);

Console.WriteLine(
    ((Success<int>)updated).Value
);
```

**Output:**

```text
20
```

### Example 3: Bind produces a failure

```csharp
Result<int> original =
    new Success<int>(-5);

Result<int> updated = Bind(
    original,
    DoublePositive
);

Console.WriteLine(
    ((Failure<int>)updated).Error
);
```

**Output:**

```text
Number must be positive
```

### Example 4: Existing failure is preserved

```csharp
Result<int> original =
    new Failure<int>("Parsing failed");

Result<int> updated = Bind(
    original,
    DoublePositive
);

Console.WriteLine(
    ((Failure<int>)updated).Error
);
```

**Output:**

```text
Parsing failed
```

`DoublePositive` is not called.

### Map vs Bind

| Map | Bind |
|---|---|
| Function returns a plain value | Function returns a Result |
| `T → R` | `T → Result<R>` |
| Transforms successful data | Connects fallible computations |
| Preserves existing failures | Preserves existing failures |
| Does not introduce a new Result from the selector | Can produce a new failure |

**Key point:** Bind composes operations that may independently succeed or fail.

## 15. Chaining Results

**Chaining Results** means connecting multiple fallible operations into a single processing pipeline.

Each stage executes only if the previous stage succeeded.

### Example 1: Parse → Validate → Calculate

The following example uses the `Result<T>`, `Success<T>`, `Failure<T>`, and `Bind()` definitions from the previous section.

```csharp
static Result<int> ParseNumber(string input)
{
    if (int.TryParse(input, out int number))
    {
        return new Success<int>(number);
    }

    return new Failure<int>("Invalid number");
}

static Result<int> ValidatePositive(int number)
{
    if (number <= 0)
    {
        return new Failure<int>(
            "Number must be positive"
        );
    }

    return new Success<int>(number);
}

static Result<int> DoubleNumber(int number)
{
    return new Success<int>(number * 2);
}
```

Usage:

```csharp
Result<int> result = Bind(
    Bind(
        ParseNumber("10"),
        ValidatePositive
    ),
    DoubleNumber
);

Console.WriteLine(
    ((Success<int>)result).Value
);
```

**Output:**

```text
20
```

### Execution

```text
"10"
  │
  ▼
ParseNumber
  │
  ▼
Success(10)
  │
  ▼
ValidatePositive
  │
  ▼
Success(10)
  │
  ▼
DoubleNumber
  │
  ▼
Success(20)
```

### Example 2: Failure during parsing

```csharp
Result<int> result = Bind(
    Bind(
        ParseNumber("ABC"),
        ValidatePositive
    ),
    DoubleNumber
);

Console.WriteLine(
    ((Failure<int>)result).Error
);
```

**Output:**

```text
Invalid number
```

The validation and calculation stages are skipped.

### Example 3: Failure during validation

```csharp
Result<int> result = Bind(
    Bind(
        ParseNumber("-5"),
        ValidatePositive
    ),
    DoubleNumber
);

Console.WriteLine(
    ((Failure<int>)result).Error
);
```

**Output:**

```text
Number must be positive
```

### Result chaining flow

```text
Start
  │
  ▼
Operation 1
  │
  ├── Failure ───────────┐
  │                      │
  ▼                      │
Operation 2              │
  │                      │
  ├── Failure ───────────┤
  │                      │
  ▼                      │
Operation 3              │
  │                      │
  ├── Failure ───────────┤
  │                      │
  ▼                      ▼
Success               Failure
```

**Key point:** Result chaining creates a fail-fast pipeline in which later operations run only after earlier operations succeed.

## 16. Fail-Fast Validation

**Fail-fast validation** stops processing when the first validation error occurs.

It is useful when later operations depend on earlier validations succeeding.

### Example 1: Validate age

```csharp
static string? ValidateAge(int age)
{
    if (age < 18)
        return "Age must be at least 18";

    if (age > 60)
        return "Age must not exceed 60";

    return null;
}

string? error = ValidateAge(15);

Console.WriteLine(error ?? "Valid");
```

**Output:**

```text
Age must be at least 18
```

### Example 2: Multiple validation rules

```csharp
static string? ValidateUser(
    string name,
    int age
)
{
    if (string.IsNullOrWhiteSpace(name))
        return "Name is required";

    if (age < 18)
        return "Age must be at least 18";

    return null;
}

string? error = ValidateUser("", 15);

Console.WriteLine(error ?? "Valid");
```

**Output:**

```text
Name is required
```

Only the first error is returned.

### Example 3: Fail-fast Result

```csharp
public abstract record Result<T>;

public sealed record Success<T>(T Value)
    : Result<T>;

public sealed record Failure<T>(string Error)
    : Result<T>;

static Result<string> ValidateName(string name)
{
    if (string.IsNullOrWhiteSpace(name))
    {
        return new Failure<string>(
            "Name is required"
        );
    }

    return new Success<string>(name);
}
```

Usage:

```csharp
Result<string> result = ValidateName("");

Console.WriteLine(
    ((Failure<string>)result).Error
);
```

**Output:**

```text
Name is required
```

### Advantages

- Stops unnecessary processing.
- Keeps sequential dependencies clear.
- Simplifies error propagation.
- Works naturally with Result binding.

### Limitations

- Reports only the first encountered error.
- May require repeated submissions to discover all validation problems.

**Key point:** Fail-fast validation returns immediately when an operation encounters its first failure.

## 17. Error Accumulation

**Error accumulation** collects multiple validation errors instead of stopping after the first one.

This is useful when validation rules are independent.

### Example 1: Collect validation errors

```csharp
static List<string> ValidateUser(
    string name,
    int age,
    string email
)
{
    List<string> errors = new();

    if (string.IsNullOrWhiteSpace(name))
    {
        errors.Add("Name is required");
    }

    if (age < 18)
    {
        errors.Add("Age must be at least 18");
    }

    if (!email.Contains('@'))
    {
        errors.Add("Invalid email");
    }

    return errors;
}

List<string> errors = ValidateUser(
    "",
    15,
    "invalid-email"
);

foreach (string error in errors)
{
    Console.WriteLine(error);
}
```

**Output:**

```text
Name is required
Age must be at least 18
Invalid email
```

### Example 2: Immutable error accumulation

```csharp
using System.Collections.Immutable;

static ImmutableArray<string> ValidateAge(int age)
{
    var errors = ImmutableArray.CreateBuilder<string>();

    if (age < 18)
    {
        errors.Add("Age is below 18");
    }

    if (age > 60)
    {
        errors.Add("Age exceeds 60");
    }

    return errors.ToImmutable();
}

var errors = ValidateAge(15);

Console.WriteLine(
    string.Join(", ", errors)
);
```

**Output:**

```text
Age is below 18
```

### Example 3: Combine independent validation results

```csharp
using System.Collections.Immutable;

static ImmutableArray<string> ValidateName(
    string name
)
{
    return string.IsNullOrWhiteSpace(name)
        ? ImmutableArray.Create("Name is required")
        : ImmutableArray<string>.Empty;
}

static ImmutableArray<string> ValidateAge(
    int age
)
{
    return age < 18
        ? ImmutableArray.Create("Age must be at least 18")
        : ImmutableArray<string>.Empty;
}

var errors = ValidateName("")
    .AddRange(ValidateAge(15));

foreach (string error in errors)
{
    Console.WriteLine(error);
}
```

**Output:**

```text
Name is required
Age must be at least 18
```

### Fail-fast vs error accumulation

| Fail-Fast | Error Accumulation |
|---|---|
| Stops at first failure | Collects multiple failures |
| Useful for dependent operations | Useful for independent validations |
| Naturally supported by Result binding | Often uses collections of errors |
| Lower unnecessary processing | More complete error reporting |
| Returns one error at a time | Can return many errors together |

**Key point:** Error accumulation evaluates independent validation rules and returns all detected problems.

## 18. Exceptions vs Explicit Results

C# supports two major approaches for communicating unsuccessful operations:

1. Throwing exceptions.
2. Returning explicit failure values.

Both approaches have appropriate uses.

### Example 1: Exception-based failure

```csharp
static int Divide(int a, int b)
{
    if (b == 0)
    {
        throw new DivideByZeroException();
    }

    return a / b;
}

try
{
    Console.WriteLine(Divide(10, 0));
}
catch (DivideByZeroException)
{
    Console.WriteLine("Division failed");
}
```

**Output:**

```text
Division failed
```

### Example 2: Explicit Result

```csharp
public abstract record Result<T>;

public sealed record Success<T>(T Value)
    : Result<T>;

public sealed record Failure<T>(string Error)
    : Result<T>;

static Result<int> Divide(int a, int b)
{
    if (b == 0)
    {
        return new Failure<int>(
            "Division by zero"
        );
    }

    return new Success<int>(a / b);
}

Result<int> result = Divide(10, 0);

Console.WriteLine(
    result switch
    {
        Success<int> success =>
            success.Value.ToString(),

        Failure<int> failure =>
            failure.Error,

        _ => throw new InvalidOperationException()
    }
);
```

**Output:**

```text
Division by zero
```

### Example 3: Try-pattern alternative

```csharp
static bool TryDivide(
    int a,
    int b,
    out int result
)
{
    if (b == 0)
    {
        result = default;
        return false;
    }

    result = a / b;
    return true;
}

bool success = TryDivide(
    10,
    0,
    out int answer
);

Console.WriteLine(success);
```

**Output:**

```text
False
```

### Comparison

| Feature | Exceptions | Explicit Results |
|---|---|---|
| Failure communication | `throw` | Return value |
| Caller handling | `try/catch` | Pattern matching or result inspection |
| Return type | Usually successful value type | Represents success and failure |
| Error information | Exception object | Error value or object |
| Expected failures | Often less convenient | Often suitable |
| Unexpected failures | Commonly suitable | May not capture every unexpected failure |
| Composition | Requires exception-aware control flow | Supports Map and Bind |
| Stack trace | Usually available | Not automatic |
| Performance | Throwing exceptions is relatively expensive | Ordinary result handling avoids exception throwing |

### When exceptions are appropriate

Exceptions are often appropriate for:

- Unexpected failures.
- Violated programming assumptions.
- Unrecoverable conditions at the current layer.
- Failures where stack traces are important.

### When explicit Results are appropriate

Explicit Results are often appropriate for:

- Expected validation failures.
- Business-rule violations.
- Parsing and conversion failures.
- Recoverable application errors.
- Functional processing pipelines.

**Key point:** Use explicit Results for expected, recoverable failures when they improve API clarity. Exceptions remain important for unexpected and exceptional conditions.

## 19. Library Types vs Custom Types

C# developers can represent absence and failure using built-in language features, custom types, or third-party functional programming libraries.

### Approach 1: Built-in nullable types

```csharp
int? score = null;

Console.WriteLine(score ?? 0);
```

**Output:**

```text
0
```

Suitable for straightforward optional values.

### Approach 2: Built-in Try pattern

```csharp
bool success = int.TryParse(
    "123",
    out int number
);

Console.WriteLine(success);
Console.WriteLine(number);
```

**Output:**

```text
True
123
```

Suitable for common parsing and lookup operations.

### Approach 3: Custom Result type

```csharp
public abstract record Result<T>;

public sealed record Success<T>(T Value)
    : Result<T>;

public sealed record Failure<T>(string Error)
    : Result<T>;
```

Usage:

```csharp
Result<int> result =
    new Success<int>(100);

Console.WriteLine(
    ((Success<int>)result).Value
);
```

**Output:**

```text
100
```

Suitable when the application needs a small, controlled abstraction.

### Approach 4: Custom Option type

```csharp
public abstract record Option<T>;

public sealed record Some<T>(T Value)
    : Option<T>;

public sealed record None<T>()
    : Option<T>;
```

Usage:

```csharp
Option<string> result =
    new Some<string>("Amit");

Console.WriteLine(
    ((Some<string>)result).Value
);
```

**Output:**

```text
Amit
```

### Approach 5: Functional programming libraries

Third-party libraries may provide ready-made abstractions such as:

- `Option<T>`
- `Result<T>`
- `Either<L,R>`
- `Map`
- `Bind`
- Pattern matching helpers

Examples of libraries offering functional programming abstractions include **LanguageExt**, **CSharpFunctionalExtensions**, and **Functional.Maybe**. Their exact types and APIs differ.

### Comparison

| Approach | Advantages | Limitations |
|---|---|---|
| Nullable types | Built into C# | Limited error information |
| Try pattern | Familiar and efficient | Less convenient for composition |
| Custom Option | Full control over representation | Requires implementation and testing |
| Custom Result | Application-specific error handling | Requires maintaining the abstraction |
| Functional libraries | Established abstractions and operators | Adds dependencies and learning requirements |

### Choosing an approach

For simple optional values:

```csharp
string?
int?
```

For parsing:

```csharp
int.TryParse(...)
```

For application-specific success and failure:

```csharp
Result<T>
```

For functional optional-value pipelines:

```csharp
Option<T>
```

For general two-case values:

```csharp
Either<L, R>
```

**Key point:** Choose the simplest representation that accurately communicates the possible outcomes of an operation.
