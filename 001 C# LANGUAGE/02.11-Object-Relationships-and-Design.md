# 02.11 Object Relationships and Design

## Association, aggregation, and composition

These are design meanings; C# does not enforce them with separate relationship keywords.

- **Association:** one object knows or uses another.
- **Aggregation:** an object groups collaborators that can exist independently.
- **Composition:** an object conceptually owns its parts and controls their lifetime or role.

```csharp
var engine = new Engine();
var car = new Car(engine); // Supplied collaborator; ownership is a design decision.
car.Start(); // Engine started

class Engine
{
    public void Start() => Console.WriteLine("Engine started");
}
class Car
{
    private readonly Engine _engine;
    public Car(Engine engine)
    {
        ArgumentNullException.ThrowIfNull(engine);
        _engine = engine;
    }
    public void Start() => _engine.Start();
}
```

A reference does not automatically determine disposal ownership. Document whether the receiving object borrows the collaborator or must dispose it.

## Dependency and delegation

A dependency is something an operation needs. Delegation means asking a collaborator to perform part of the work, as `Car.Start` delegates to `Engine.Start`.

Passing a collaborator as a method parameter can express a short-lived dependency. Storing it in a field expresses a dependency used across the object's operations.

## Coupling and cohesion

Coupling measures how strongly components depend on each other's details. Cohesion describes how closely a component's responsibilities belong together.

Keep invoice calculation with invoice rules; keep SMTP configuration and network delivery in a sender. One class handling both is harder to change and verify independently.

## Constructor dependency injection

Supply dependencies when constructing an object instead of creating hidden concrete dependencies inside its methods.

```csharp
var checkout = new Checkout(new ConsoleReceiptSender());
checkout.Complete("ORDER-1"); // Receipt: ORDER-1

interface IReceiptSender
{
    void Send(string orderId);
}
class ConsoleReceiptSender : IReceiptSender
{
    public void Send(string orderId) => Console.WriteLine($"Receipt: {orderId}");
}
class Checkout
{
    private readonly IReceiptSender _sender;
    public Checkout(IReceiptSender sender)
    {
        ArgumentNullException.ThrowIfNull(sender);
        _sender = sender;
    }
    public void Complete(string orderId)
    {
        ArgumentException.ThrowIfNullOrWhiteSpace(orderId);
        _sender.Send(orderId);
    }
}
```

A dependency-injection container is optional; the example performs injection directly with constructors.

## Responsibilities and collaborations

- Give each class a coherent reason to change.
- Put validation near the state or operation whose rule it protects.
- Depend on a contract when implementations must be replaceable.
- Avoid circular dependencies; move a shared responsibility to a suitable collaborator.
- Keep object ownership explicit, especially for disposable resources.
- Do not create deep inheritance merely to reuse a few methods; a helper or composed service can express reuse more clearly.
