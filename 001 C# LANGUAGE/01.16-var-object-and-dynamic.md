# 01.16 var, object, and dynamic

## Explicit typing versus inference

`var` asks the compiler to infer a local variable's static type from its initializer. It does not make the variable dynamically typed.

```csharp
int first = 10;
var second = 20; // Also int.
Console.WriteLine(first.GetType() == second.GetType()); // True

// second = "Twenty"; // Compile-time error: second remains int.
```

Use explicit types when they make the intended contract clearer; use `var` when the initializer makes the type obvious.

## var rules and limitations

```csharp
var name = "Deep";        // string
var values = new[] { 1, 2 }; // int[]
var price = 12.5M;         // decimal
Console.WriteLine($"{name}: {values.Length}, {price}");

// var empty;           // Error: no initializer.
// var unknown = null;  // Error: null alone does not identify a type.
// var x = 1, y = 2;    // Error: multiple declarators are not allowed.
```

`var` is used in supported local declarations and patterns, not as an ordinary field, method return type, or parameter type. In a modern C# version, some lambdas and method groups have an inferable natural delegate type; this is still compile-time typing.

## Anonymous types

An anonymous type packages named read-only properties without declaring a named class.

```csharp
var product = new { Name = "Book", Price = 20M };
Console.WriteLine(product.Name);  // Book
Console.WriteLine(product.Price); // 20
// product.Price = 30M; // Error: generated properties are read-only.
```

- `var` lets the compiler retain the generated type.
- Property values may refer to mutable objects; read-only properties do not imply deep immutability.
- Use a named record or class when a value must form a clear public API contract.

## object and runtime checks

`object` can hold a reference to any reference type or a boxed value type. Member access is checked against `object` at compile time.

```csharp
object value = "Hello";
// Console.WriteLine(value.Length); // Error: object has no Length property.
if (value is string text)
    Console.WriteLine(text.Length); // 5

value = 42; // int is boxed.
Console.WriteLine((int)value + 1); // 43: exact unboxing type.
```

A wrong cast can fail at runtime. Prefer a type pattern when the type is uncertain.

## dynamic and runtime binding

`dynamic` postpones supported member and operation binding until execution.

```csharp
dynamic value = "Hello";
Console.WriteLine(value.Length); // 5: resolved at runtime.
value = 42;
Console.WriteLine(value + 1); // 43
// Console.WriteLine(value.Length); // RuntimeBinderException: int has no Length.
```

Misspelled members can compile and fail only when the statement runs. Dynamic overload resolution uses the runtime argument types.

```csharp
dynamic argument = "hello";
Console.WriteLine(Formatter.Format(argument)); // String

static class Formatter
{
    public static string Format(object value) => "Object";
    public static string Format(string value) => "String";
}
```

## Choosing between them

| Form | Compile-time type checking | Typical purpose |
| --- | --- | --- |
| `var` | Full checking of inferred type | Shorter local declarations |
| `object` | Checking against `object`; narrow explicitly | Heterogeneous values and general APIs |
| `dynamic` | Selected binding deferred to runtime | Interop or deliberately dynamic object models |

```csharp
var inferred = "C#";
object general = "C#";
dynamic lateBound = "C#";
Console.WriteLine(inferred.Length); // 2
Console.WriteLine(((string)general).Length); // 2
Console.WriteLine(lateBound.Length); // 2
```

For normal application models, prefer concrete types or interfaces. `dynamic` does not remove the need to understand which operations the actual object supports.
