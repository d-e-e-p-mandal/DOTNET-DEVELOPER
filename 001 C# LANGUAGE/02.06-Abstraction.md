# 02.06 Abstraction

## Capabilities versus implementation

Abstraction exposes what callers can do while hiding details they do not need. A caller can request delivery without knowing how a specific sender transmits a message.

```csharp
INotifier notifier = new ConsoleNotifier();
notifier.Send("Order accepted"); // Notice: Order accepted

interface INotifier
{
    void Send(string message);
}
class ConsoleNotifier : INotifier
{
    public void Send(string message) => Console.WriteLine($"Notice: {message}");
}
```

The interface is the caller's contract; the class supplies the implementation.

## Contracts and implementation details

A useful contract describes accepted inputs, observable results, failures, and ownership when relevant. Method signatures alone cannot express every rule.

For `Send(string message)`, decide whether null is invalid, whether completion means queued or delivered, and how failure is reported. Callers should not need to inspect the implementation to discover these expectations.

## Abstract classes and members

An abstract class cannot be instantiated. It can combine state, implemented members, and members that derived concrete classes must implement.

```csharp
Shape shape = new Rectangle(4, 3);
Console.WriteLine(shape.Describe()); // Area: 12

abstract class Shape
{
    public abstract double Area { get; }
    public string Describe() => $"Area: {Area}";
}
class Rectangle : Shape
{
    private readonly double _width;
    private readonly double _height;
    public Rectangle(double width, double height)
    {
        if (width <= 0 || height <= 0)
            throw new ArgumentOutOfRangeException(nameof(width));
        _width = width;
        _height = height;
    }
    public override double Area => _width * _height;
}
```

- `abstract` members have no implementation body.
- Concrete derived classes must implement inherited abstract members.
- An abstract class can have a constructor for shared initialization.
- Abstract members participate in overriding; do not also mark them `virtual`.

## Choosing abstraction boundaries

Use an interface for a capability that different kinds of objects can implement. Use an abstract base when related types benefit from shared implementation or state and a genuine inheritance relationship exists.

Keep the contract focused. An interface with unrelated database, email, file, and UI operations couples clients to too many responsibilities. Avoid adding an interface merely to copy every public method of a class when no useful boundary exists.

A good replacement honors the same meaning, not only the same signature. An implementation that silently drops every message can satisfy the compiler while violating the intended delivery contract.
