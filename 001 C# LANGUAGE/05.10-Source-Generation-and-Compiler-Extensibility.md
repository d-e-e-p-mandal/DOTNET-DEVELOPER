# 05.10 Source Generation and Compiler Extensibility

## Runtime reflection versus compile-time generation

Reflection discovers metadata while a program runs. A source generator analyzes compilation inputs and adds C# source during compilation.

Generated code is then compiled with ordinary source. Generators do not rewrite arbitrary existing source files or magically discover every runtime value.

## A working generated member

The built-in regular-expression generator creates the implementation of this partial method:

```csharp
using System.Text.RegularExpressions;

Console.WriteLine(Patterns.Code().IsMatch("AB123")); // True
Console.WriteLine(Patterns.Code().IsMatch("invalid")); // False

partial class Patterns
{
    [GeneratedRegex(@"\A[A-Z]{2}[0-9]{3}\z", RegexOptions.CultureInvariant)]
    public static partial Regex Code();
}
```

The declaration and attribute are your input; generated implementation code supplies the missing method body during an SDK build. No manual implementation file is required.

## Roslyn syntax trees and semantic models

A syntax tree describes parsed source structure. A semantic model explains meaning within a compilation: symbols, types, overloads, and conversions.

For direct Roslyn API use, add its compiler package to a separate tooling project:

```bash
dotnet add package Microsoft.CodeAnalysis.CSharp --version 4.14.0
```

```csharp
using Microsoft.CodeAnalysis.CSharp;
using Microsoft.CodeAnalysis.CSharp.Syntax;

var tree = CSharpSyntaxTree.ParseText("class Customer { public int Id; }");
var declaration = tree.GetRoot().DescendantNodes()
    .OfType<ClassDeclarationSyntax>().Single();
Console.WriteLine(declaration.Identifier.ValueText); // Customer
```

Parsing alone cannot prove which external type a name resolves to. Create a compilation with appropriate references and obtain its semantic model when symbol identity matters.

## Incremental generator concepts

An incremental generator implements `IIncrementalGenerator`. Its `Initialize` method connects input providers, transformations, and source-output registration.

Typical pipeline:

```text
Relevant syntax or attributes
    → semantic information
    → small immutable generation model
    → deterministic generated source
```

Keep transformations focused so unchanged inputs can reuse cached work. Avoid hidden mutable state, machine-specific paths, timestamps, or unnecessary compilation-wide dependencies.

## Generated partial types and members

Partial declarations provide an intentional place for generated code to extend a type. The generator must reproduce compatible namespace, containing types, generic parameters, accessibility, and member signatures.

Use stable generated filenames and fully qualified type names where name collisions are possible. Do not generate duplicates for the same symbol encountered through several syntax declarations.

## Diagnostics and analyzers

A diagnostic has an identifier, severity, message, and usually a source location. Report actionable input problems instead of emitting invalid code and leaving confusing downstream compiler errors.

An analyzer reports code issues; a generator emits source. A code fix offers a source edit through tooling. These roles can cooperate but are not interchangeable.

## Generator engineering boundaries

A production generator needs a separate analyzer-style project, compiler-host-compatible dependencies, tests for generated output and diagnostics, cancellation support, and a packaging strategy. Keep detailed incremental pipeline and packaging implementation in the dedicated Roslyn group; this lesson establishes how generation participates in a normal C# build.
