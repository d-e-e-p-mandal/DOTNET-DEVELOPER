# 01.02 Development Environment and First Program

**Goal:** install the tools, create a C# console application, understand its files, run it, and fix basic errors.

**Examples use:** .NET 10 SDK, `net10.0`, and C# 14. Commands work in a terminal on macOS, Windows, or Linux unless marked otherwise.

## 1. Installing and Checking the .NET SDK

### What should you install?

Install the **.NET SDK** to write, build, and run C# applications. It includes development tools and the corresponding runtime. Installing only the runtime is insufficient for development.

### Install on macOS

1. Open **Apple menu → About This Mac** and check your chip or processor.
2. On Microsoft's .NET download page, select **.NET 10 → SDK → macOS installer**.
3. Choose **Arm64** for Apple silicon, such as M1/M2/M3/M4, or **x64** for an Intel Mac.
4. Open the downloaded `.pkg` file and complete the installer.
5. Close and reopen Terminal, then run the checks below.

### Install on Windows

Choose the **.NET 10 SDK Windows installer**, select the architecture matching your computer, and complete installation. Reopen your terminal afterward. Installing through Visual Studio is also possible.

### Check the installation

```bash
dotnet --version
dotnet --list-sdks
dotnet --list-runtimes
dotnet --info
```

| Command | What it tells you |
|---|---|
| `dotnet --version` | SDK selected for the current directory |
| `dotnet --list-sdks` | All SDKs found by this `dotnet` installation |
| `dotnet --list-runtimes` | Installed runtimes found by this installation |
| `dotnet --info` | SDK, runtime, operating system, architecture, and paths |

An SDK version such as `10.0.201` is normal. SDK and runtime version numbers need not be identical.

**If `dotnet` is not found:** reopen the terminal, confirm that you installed the SDK, and check whether its installation directory is on `PATH`. `PATH` is the list of directories your terminal searches for commands.

**If an unexpected SDK is selected:** a `global.json` file in the current directory or a parent directory may select a particular SDK.

## 2. Visual Studio, VS Code, and Rider

An **editor** helps you write code. An **IDE** combines editing with project management, building, and debugging.

| Tool | Platforms | Basic setup |
|---|---|---|
| Visual Studio | Windows | For .NET 10, use Visual Studio 2026 18.0 or later with the .NET desktop development workload |
| Visual Studio Code | Windows, macOS, Linux | Install VS Code and Microsoft's C# Dev Kit extension |
| JetBrains Rider | Windows, macOS, Linux | Install Rider and open the project file |

Choose one tool. All three can work with a C# `.csproj` project.

### Simple setup using VS Code

1. Install VS Code.
2. Open **Extensions**, search for **C# Dev Kit**, and install the Microsoft extension.
3. Create the project using the commands in Section 3.
4. Select **File → Open Folder** and open the `HelloCSharp` folder.
5. Open `Program.cs` and use **Terminal → New Terminal** to run commands.

Open the whole project folder so the editor can find the `.csproj` file and understand the project.

## 3. Create, Build, Run, and Publish

### Create a console project

Open a terminal in the directory where you want to keep your practice projects:

```bash
dotnet new console -n HelloCSharp -f net10.0
cd HelloCSharp
```

| Part | Meaning |
|---|---|
| `dotnet` | Starts the .NET command-line tool |
| `new console` | Creates an application that runs in a terminal |
| `-n HelloCSharp` | Sets the project name and, here, its folder name |
| `-f net10.0` | Targets .NET 10 |
| `cd HelloCSharp` | Moves the terminal into the project folder |

The template creates the source and project files and normally restores dependencies automatically.

### Build: check and compile

```bash
dotnet build
```

The build checks the source and produces compiled output. A successful build reports `Build succeeded.` It does **not** execute your program.

The default output for this project includes:

```text
bin/Debug/net10.0/HelloCSharp.dll
```

### Run: build and execute

```bash
dotnet run
```

Expected application output from the original template:

```text
Hello, World!
```

`dotnet run` builds when needed, then starts the application. You do not need to run `build` separately every time.

```bash
dotnet run --no-build
```

This uses existing build output. After changing code, omit `--no-build` so your changes are compiled.

### Debug and Release configurations

```bash
dotnet build -c Release
dotnet run -c Release
```

**Debug** is the default development configuration. **Release** normally enables compiler optimizations. `-c` means configuration; it does not select a Development, Staging, or Production environment.

### Publish: prepare files for deployment

Run from the `HelloCSharp` project folder:

```bash
dotnet publish -c Release --self-contained false -o publish
dotnet ./publish/HelloCSharp.dll
```

- `publish` prepares the application and its required deployment files.
- `--self-contained false` leaves the .NET runtime out of the output. The destination computer needs a compatible runtime.
- `-o publish` places the deployment files in a folder named `publish`.
- `dotnet ./publish/HelloCSharp.dll` executes the published application.

Copy the **complete publish folder** when deploying; the DLL may need accompanying files and dependencies.

**Restore** resolves project dependencies. These commands usually restore automatically when necessary; run `dotnet restore` separately only when you need that step by itself.

## 4. Project Folder, Program.cs, and .csproj

After building and publishing, the folder contains:

```text
HelloCSharp/
├── Program.cs
├── HelloCSharp.csproj
├── obj/
├── bin/
│   ├── Debug/net10.0/
│   └── Release/net10.0/
└── publish/
```

| File or folder | Purpose |
|---|---|
| `Program.cs` | C# source code for this application's starting point |
| `HelloCSharp.csproj` | Project settings written in XML |
| `obj/` | Generated intermediate files and dependency information |
| `bin/` | Compiled build output |
| `publish/` | Deployment output created by our publish command |

Edit source and project files. `bin` and `obj` are generated and can be recreated by building.

### Understand the project file

```xml
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <OutputType>Exe</OutputType>
    <TargetFramework>net10.0</TargetFramework>
    <ImplicitUsings>enable</ImplicitUsings>
    <Nullable>enable</Nullable>
  </PropertyGroup>
</Project>
```

| Setting | Meaning |
|---|---|
| `Sdk="Microsoft.NET.Sdk"` | Uses standard .NET build rules |
| `PropertyGroup` | Groups project settings |
| `OutputType` | `Exe` makes a runnable application; it does not mean every output file has an `.exe` extension |
| `TargetFramework` | Selects the target platform and its available APIs |
| `ImplicitUsings` | Automatically imports common namespaces, including `System` |
| `Nullable` | Enables nullable reference type annotations and compiler analysis |

Nullable analysis helps identify possible null mistakes; it does not prevent every null error at runtime.

## 5. Target Framework and Language Version

These are separate settings:

| Term | Controls | Example |
|---|---|---|
| SDK version | Tools used to build the project | `10.0.201` |
| Target framework | .NET APIs and runtime target | `net10.0` |
| C# language version | Language syntax and features accepted by the compiler | C# 14 |

For `net10.0`, the default language version is **C# 14**. Normally, leave `LangVersion` unspecified and let the target framework choose the appropriate default.

If a project specifically requires an explicit language version, add this inside `PropertyGroup`:

```xml
<LangVersion>14.0</LangVersion>
```

Setting `LangVersion` does not install an SDK or change the runtime target. Avoid `latest` for a shared project when you need a predictable language version across machines.

An SDK must support your target framework. A .NET 8 SDK cannot build a project targeting `net10.0`. If you see an unsupported target framework error, check the selected SDK with `dotnet --version`.

## 6. Hello World and Program Execution

### Your first complete program

Replace the contents of `Program.cs` with:

```csharp
Console.WriteLine("Hello, World!");
Console.WriteLine("I am learning C#.");
```

Save the file and run `dotnet run` from the project folder.

```text
Hello, World!
I am learning C#.
```

| Code | Meaning |
|---|---|
| `Console` | .NET type for interacting with the terminal |
| `WriteLine` | Method that writes a value followed by a new line |
| `"Hello, World!"` | String: text enclosed in double quotes |
| `( ... )` | Supplies arguments to the method |
| `;` | Ends this statement |

C# is case-sensitive: `Console.WriteLine` and `console.writeline` are different names.

### Top-level statements and Main

The example uses **top-level statements**: executable code written without declaring a `Main` method yourself. The compiler creates an entry point.

The traditional equivalent is:

```csharp
using System;

class Program
{
    static void Main()
    {
        Console.WriteLine("Hello, World!");
        Console.WriteLine("I am learning C#.");
    }
}
```

Use either version as the complete `Program.cs`; do not paste both together. `Main` is the traditional entry point, and its braces contain the statements to execute. Only one source file per project can contain top-level statements.

For this simple program, execution enters the generated entry point or `Main`, runs statements from top to bottom, and exits after the last statement.

### Read input and display a result

Replace `Program.cs` with this complete example:

```csharp
Console.Write("Enter your name: ");       // Keep the cursor on this line.
string name = Console.ReadLine() ?? "Learner"; // Read input; handle null.
Console.WriteLine($"Hello, {name}!");     // Insert the name into the text.
```

Example terminal interaction:

```text
Enter your name: Deep
Hello, Deep!
```

- `Write` prints without adding a new line.
- `ReadLine` waits for a line of input in an interactive terminal.
- `?? "Learner"` supplies a fallback if the result is `null`. Pressing Enter on an empty line produces an empty string, not this fallback.
- `$"...{name}..."` inserts the variable's value into the string.

## 7. Compile-Time Errors, Runtime Errors, and Logic Errors

### Compile-time error: the program cannot build

**Incorrect — missing semicolon:**

```csharp
Console.WriteLine("Hello")
```

The compiler reports an error such as `CS1002: ; expected`.

**Fix:**

```csharp
Console.WriteLine("Hello");
```

Use the file name and line number in the build message to locate the mistake. Fix the first error and build again; later errors may be consequences of it.

### Runtime error: the program builds but fails while running

**Deliberately failing example:**

```csharp
int divisor = 0;
Console.WriteLine(10 / divisor);
```

This builds, but integer division by zero throws `DivideByZeroException` during execution.

**Fix — check before dividing:**

```csharp
int divisor = 0;

if (divisor == 0)
{
    Console.WriteLine("Cannot divide by zero.");
}
else
{
    Console.WriteLine(10 / divisor);
}
```

Output: `Cannot divide by zero.`

### Logic error: the program runs but gives the wrong result

```csharp
int price = 100;
int quantity = 2;
int total = price + quantity; // Wrong operation for a purchase total.
Console.WriteLine(total);     // Actual: 102. Expected: 200.
```

**Fix:** replace the calculation with `int total = price * quantity;`.

The compiler cannot know the business rule you intended. Check results against known examples.

### Find mistakes with a debugger

1. Click beside a line number to set a **breakpoint**.
2. Start the project with your editor's **Debug** action.
3. When execution pauses, inspect variables such as `price` and `quantity`.
4. Use **Step Over** to execute one statement and check how values change.

| Error type | When you notice it | First check |
|---|---|---|
| Compile-time | Build fails | Syntax, names, and types |
| Runtime | Execution throws or fails | Exception message, stack trace, and inputs |
| Logic | Output is incorrect | Expected result, calculations, and conditions |

**Practice:** create the project, run the greeting, build it in Release, publish it, and execute the published DLL. Try each error example separately, then apply its fix.
