# 01.07 Values, References, and Copying

## 1. Value Types versus Reference Types

**Value-type variables** contain their values. **Reference-type variables** contain references to objects, or `null`.

| Category | Examples | Ordinary assignment copies |
|---|---|---|
| Value types | `int`, `double`, `decimal`, `bool`, `char`, structs, enums | The value |
| Reference types | Classes, arrays, `string`, `object`, `List<T>` | The reference |

```csharp
int score = 90;           // Value-type variable.
int[] marks = { 70, 80 }; // Reference to an array object.
string name = "Deep";    // Reference to a string object.

Console.WriteLine(score);    // 90
Console.WriteLine(marks[0]); // 70
```

An `int[]` is a reference type even though its elements are value types. `var` does not change a type's value/reference behavior.

## 2. Copying a Value versus Copying a Reference

### Copying a value

```csharp
int first = 10;
int second = first; // Copy the number.
second = 20;

Console.WriteLine(first);  // 10
Console.WriteLine(second); // 20
```

Changing `second` does not change `first`.

### Copying a reference

```csharp
int[] first = { 10 };
int[] second = first; // Both refer to the same array.
second[0] = 20;

Console.WriteLine(first[0]);  // 20
Console.WriteLine(second[0]); // 20
```

The array was not copied. Both variables access the same object.

### Reassigning a reference

```csharp
int[] first = { 10 };
int[] second = first;
second = new int[] { 99 }; // second now refers to a different array.

Console.WriteLine(first[0]);  // 10
Console.WriteLine(second[0]); // 99
```

**Mutation** changes an object. **Reassignment** changes which object a variable references.

## 3. Object Identity versus Value Equality

- **Identity:** are these references pointing to the same object?
- **Value equality:** are their contents equal according to the type's comparison rules?

```csharp
string first = new string('A', 3);
string second = new string('A', 3);
string same = first;

Console.WriteLine(first == second); // True: both contain AAA.
Console.WriteLine(object.ReferenceEquals(first, second)); // False.
Console.WriteLine(object.ReferenceEquals(first, same));   // True.
```

The two separately created strings have equal text but different identities.

### Comparison depends on the type

```csharp
object first = new string('A', 3);
object second = new string('A', 3);

Console.WriteLine(first == second);      // False: object == checks identity.
Console.WriteLine(first.Equals(second)); // True: string's Equals checks text.
```

`==` uses the applicable operator based on the operands' compile-time types. Virtual `Equals` can use the runtime type's implementation.

- Ordinary classes inherit identity-based equality unless they customize it.
- Strings compare text with `==`; record classes provide value equality by default.
- Structs have field-based equality by default through `Equals`, but a custom struct does not automatically get a usable `==` operator.
- Use `ReferenceEquals` for identity checks on references, not value-type comparisons that would trigger boxing.

## 4. Mutation and Shared References

### Method arguments also copy values by default

```csharp
int[] marks = { 10 };
Update(marks);
Console.WriteLine(marks[0]); // 90

void Update(int[] values)
{
    values[0] = 90;             // Mutate the shared array.
    values = new int[] { 100 }; // Reassign only the local parameter.
}
```

The parameter receives a copy of the reference. It can change the shared object, but reassigning it does not replace the caller's `marks` reference. A reference-type argument is not automatically passed with `ref`.

### A struct can contain shared references

```csharp
Report first = new Report { Score = 10, Tags = new string[] { "A" } };
Report second = first;

second.Score = 20;    // Change the copied integer field.
second.Tags[0] = "B"; // Change the array shared by both structs.

Console.WriteLine(first.Score);   // 10
Console.WriteLine(first.Tags[0]); // B

struct Report
{
    public int Score;
    public string[] Tags;
}
```

Struct assignment copies each field's value. A reference field's value is a reference, so its object remains shared. This is not a deep copy of all nested objects.

Strings are immutable: assigning new text to a shared string variable does not modify the original string object.

## 5. Boxing and Unboxing

**Boxing** stores a copy of a value-type value in an object. **Unboxing** extracts the matching value type from that boxed object.

```csharp
int original = 10;
object boxed = original; // Box a copy of 10.
original = 20;

int unboxed = (int)boxed; // Extract 10 into another local.
unboxed = 30;

Console.WriteLine(original); // 20
Console.WriteLine(boxed);    // 10
Console.WriteLine(unboxed);  // 30
```

Changing either integer local does not change the boxed value.

### Unbox to the correct type first

```csharp
object boxed = 10; // Contains a boxed int.

// long wrong = (long)boxed; // Throws InvalidCastException.
long correct = (int)boxed;  // Unbox as int, then convert to long.

Console.WriteLine(correct); // 10
```

- A boxed `int` cannot be directly unboxed as `long`, even though `long` can hold its number.
- Unboxing `null` to a non-nullable value type throws `NullReferenceException`.
- Converting a value type to an implemented interface can also box it.
- Boxing normally adds an allocation. A collection such as `List<int>` stores integers without boxing each element; `List<object>` boxes integers added to it.

## 6. Why Value Types Do Not Always Mean Stack Storage

**Value type** describes value and copying behavior. It does not promise a stack location.

```csharp
Holder holder = new Holder { Count = 10 };
int[] counts = { 20 };
object boxed = 30;

Console.WriteLine(holder.Count + counts[0] + (int)boxed); // 60

class Holder
{
    public int Count; // Value-type field inside a reference-type object.
}
```

| Situation | Usual storage |
|---|---|
| Local `int` | Stack location, CPU register, or optimized away |
| `int` field in a class object | Inside the object, normally on the managed heap |
| Elements of `int[]` | Inside the array object, normally on the managed heap |
| Boxed `int` | Inside a boxed object, normally on the managed heap |

Captured locals and values retained across asynchronous work may also become fields in heap objects. Runtime optimizations can change physical allocation without changing the program's required behavior.

A local reference and the object it references are separate: storing the reference locally does not place the entire object on the stack.
