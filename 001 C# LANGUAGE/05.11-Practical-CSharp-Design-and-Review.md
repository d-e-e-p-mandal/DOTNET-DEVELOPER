# 05.11 Practical C# Design and Review

## Choosing the type shape

Choose a class for shared identity and controlled mutable behavior. Choose a struct for a small value, a record for useful value-oriented generated behavior, and an interface for a replaceable capability.

```csharp
readonly record struct ProductId(int Value);
record ProductSummary(ProductId Id, string Name);
interface IPriceRule { decimal Apply(decimal subtotal); }
```

These choices answer different questions: value representation, data transfer, and behavior contract.

## Ownership, nullability, and mutation

```csharp
var cart = new Cart();
cart.Add("Book");
IReadOnlyList<string> snapshot = cart.Snapshot();
cart.Add("Pen");
Console.WriteLine(snapshot.Count); // 1: independent list of current strings.

class Cart
{
    private readonly List<string> _items = new();
    public void Add(string item)
    {
        ArgumentException.ThrowIfNullOrWhiteSpace(item);
        _items.Add(item);
    }
    public IReadOnlyList<string> Snapshot() => _items.ToArray();
}
```

The snapshot does not expose the internal list. A readonly interface alone would not create a snapshot, and copying a collection of mutable objects would still share those object references.

## Generic APIs and equality

Use generics when the algorithm is truly independent of a specific type. State required capabilities through constraints and accept equality comparers when callers need a policy choice.

```csharp
Console.WriteLine(HasDuplicate(new[] { "A", "a" }, StringComparer.OrdinalIgnoreCase)); // True

bool HasDuplicate<T>(IEnumerable<T> source, IEqualityComparer<T>? comparer = null)
{
    ArgumentNullException.ThrowIfNull(source);
    var seen = new HashSet<T>(comparer);
    foreach (T value in source)
        if (!seen.Add(value)) return true;
    return false;
}
```

This enumerates once and stops at the first duplicate. It does not require sorting or materializing the entire source first.

## Reflection, dynamic, and unsafe code

Prefer normal typed calls when the operation and types are known. Use reflection for genuine metadata-driven behavior, dynamic for a deliberate runtime binding boundary, and unsafe code for a justified native or low-level requirement. Each choice should have a specific reason and a testable contract.

## Allocation, copying, and lifetime review

Check whether loops allocate unnecessarily, whether closures retain large objects, whether struct copies are expensive, and whether pooled buffers outlive their lease. Measure representative workloads before replacing readable code with a more complicated version.

A value type is not automatically allocation-free; a read-only reference is not automatically immutable; garbage collection is not deterministic disposal.

## Building and testing a reusable library

```bash
dotnet new classlib -n Catalog
dotnet new xunit -n Catalog.Tests
dotnet add Catalog.Tests/Catalog.Tests.csproj reference Catalog/Catalog.csproj
dotnet build Catalog/Catalog.csproj -c Release
dotnet test Catalog.Tests/Catalog.Tests.csproj -c Release
```

The test template restores its test dependencies. Put reusable types in the library and behavioral tests in the test project.

Cover public behavior: valid results, invalid input, null contracts, equality consistency, empty collections, ownership boundaries, and state after failure. Build every advertised target framework and verify public APIs from a separate consumer project. Avoid tests that only repeat the implementation line for line.
